### 1. Data Thread 📊

> 1/7 Git config vulnerabilities affect **7 AI coding agents** when you `git clone` + run an agent.
>
> 4 remain **unpatched** as of Oct 2026.
>
> Affected: Claude Code, Codex CLI, Cursor, Aider, Opencode, Goose, Kilo Code.
>
> The blast radius: any `git clone` → agent run = attack surface.
>
> 🧵 Thread on the 8 CVEs and what to do:

> 2/7 The core problem: agents read `.git/config` to understand repos. Git configs like `core.sshCommand`, `credential.helper`, `filter.<name>.clean/smudge` execute commands.
>
> **Agents don't sanitize these.** When they run `git status/diff/commit` → malicious config executes on YOUR machine with YOUR permissions.

> 3/7 Patch status (Oct 2026):
> ✅ Claude Code v2.1.280+ (3 CVEs patched)
> ✅ Codex CLI v0.160+
> ✅ Aider v0.84+
> ⚠️ Cursor — partially patched
> ❌ Opencode, Goose, Kilo Code — unpatched

> 4/7 CVE-2026-24887, CVE-2026-25723, CVE-2026-35022 — the three hitting Claude Code.
>
> If you clone repos and run agents, you're exposed. Supply chain compromise or debugging a dependency's repo = same risk.

> 5/7 Immediate mitigations:
> • `git config --global core.fsmonitor false`
> • `git config --global credential.helper ""`
> • Audit `.git/config` before running agents on cloned repos
> • Use `GIT_CONFIG_NOSYSTEM=1` to ignore system configs

> 6/7 Long-term: agents need config sanitization. Until then, **treat every cloned repo as untrusted input**.
>
> Our full breakdown with the table of 7 agents, 8 vulns, and patch links: terminalblog.com/blog/beware-malicious-git-configs-run-attacker-code-claude-codex-cursor/

> 7/7 The uncomfortable truth: we trusted agents with our terminals. Now we know they trust Git configs too much.
>
> Bookmark this thread. Share with your team. Audit your workflows.
>
> Security isn't a feature — it's the floor.

### 4. Hot Take 🔥

> Hot take: **AI coding agents are the new package managers** — and we're repeating every npm supply-chain mistake.
>
> `git clone` → `agent run` = `npm install` with root access to your terminal.
>
> We sandbox npm. We don't sandbox agents. Yet.
>
> The first agent with a proper capability sandbox (filesystem, network, exec allowlists) wins the enterprise. Not the one with the best model. The one that *can't* run `rm -rf /` when a repo asks it to.
