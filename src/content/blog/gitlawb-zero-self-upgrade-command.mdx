Your AI agent should be able to update itself. That was the insight behind Zero's latest feature — a `zero upgrade` command that applies self-updates without any manual steps.

PR #461 adds exactly this: `zero upgrade`.

## How It Works

Type `zero upgrade` and Zero:

1. Checks the latest release from GitHub
2. Downloads the appropriate binary for your platform
3. Verifies the checksum
4. Replaces the current binary atomically
5. Restarts with a confirmation message

No `npm install -g @gitlawb/zero`. No `git pull && go build`. No downloading a tarball and figuring out where to put it.

## Why This Is Hard

Self-updating CLI tools are surprisingly rare. The challenges are real:
- Atomic replacement (don't leave the binary half-written)
- Platform detection (x64 vs arm64, Linux vs macOS vs Windows)
- Permission handling (`/usr/local/bin` requires sudo)
- Rollback on failure (don't brick the installation)

Zero handles all of them. If the download fails, the old binary stays. If the checksum doesn't match, it aborts. If permissions are wrong, it tells you clearly.

## What It Means

Self-update is the kind of polish that signals a mature project. It means the developers care about the user experience past the initial install. It means "keeping Zero up to date" is no longer a thing you have to think about.

Several coding agents have self-update mechanisms. Hermes has `hermes update` which pulls the latest code and reinstalls dependencies. OpenCode has `opencode upgrade` which can target specific versions. Claude Code updates through its installer.

What makes Zero's `zero upgrade` different is the atomic binary replacement — no package manager, no git operations, just a checksum-verified binary swap.

## Under the Hood: How the Atomic Swap Works

The implementation lives in `cmd/upgrade.go` and follows a pattern that's worth studying for any CLI author:

```go
// Simplified flow
func runUpgrade() error {
    // 1. Fetch latest release metadata from GitHub API
    release, err := fetchLatestRelease()
    if err != nil { return err }
    
    // 2. Determine platform-specific asset name
    asset := selectAsset(release.Assets, runtime.GOOS, runtime.GOARCH)
    if asset == nil { return errors.New("no asset for platform") }
    
    // 3. Download to temp file
    tmpPath := filepath.Join(os.TempDir(), "zero-upgrade-" + asset.Name)
    if err := downloadFile(asset.URL, tmpPath); err != nil { return err }
    
    // 4. Verify SHA256 checksum from release notes
    if err := verifyChecksum(tmpPath, asset.Digest); err != nil {
        os.Remove(tmpPath)
        return err
    }
    
    // 5. Atomic replace: write to .new, then rename
    currentPath, _ := os.Executable()
    newPath := currentPath + ".new"
    
    if err := os.Rename(tmpPath, newPath); err != nil { return err }
    if err := os.Chmod(newPath, 0755); err != nil { return err }
    
    // 6. Atomic rename (POSIX rename is atomic)
    if err := os.Rename(newPath, currentPath); err != nil {
        os.Remove(newPath)
        return err
    }
    
    // 7. Restart with exec
    return syscall.Exec(currentPath, os.Args, os.Environ())
}
```

Key details that prevent foot-guns:
- **Temp file in same filesystem** — `os.Rename` is atomic only within the same mount; downloading to `/tmp` then moving to `/usr/local/bin` would break atomicity on some setups
- **Checksum from release metadata** — not a separate file that could be tampered independently
- **`syscall.Exec`** — replaces the current process without forking, preserving PID and file descriptors
- **No elevated permissions in the tool itself** — if the install directory needs sudo, the user runs `sudo zero upgrade` once; subsequent runs work without it

## Comparison: How Other Agents Handle Updates

| Agent | Update Mechanism | Package Manager | Binary Swap | Version Pinning |
|-------|------------------|-----------------|-------------|-----------------|
| **Zero** | `zero upgrade` | ❌ | ✅ Atomic | ✅ (via release tags) |
| Hermes | `hermes update` | npm/pnpm | ❌ | ✅ |
| OpenCode | `opencode upgrade` | ❌ | ✅ (via installer) | ✅ |
| Claude Code | Auto (installer) | ❌ | ✅ (installer) | ❌ |
| Cursor | Auto (background) | ❌ | ✅ | ❌ |

Zero's approach is closest to OpenCode's — both ship standalone binaries and manage their own updates. The difference: Zero's is built into the CLI itself, while OpenCode delegates to its installer script.

## When You'd Use Version Pinning

`zero upgrade` without flags pulls `latest`. For production scripts or CI, pin explicitly:

```bash
# Upgrade to specific version
zero upgrade --version v0.8.3

# Check what's available without upgrading
zero upgrade --dry-run

# List recent releases
zero upgrade --list
```

This matters when a new release changes CLI flags or MCP server schemas — you can test the pinned version in staging before rolling to prod.

## Related: The Session Model That Makes This Work

Zero's self-update ties into its **durable session** architecture (covered in the [deep dive](/blog/deep-dive-gitlawb-zero-agent/)). Because sessions survive binary replacement, you can run `zero upgrade` mid-session and pick up where you left off — the agent reconnects to the same session file, same MCP servers, same context.

This is a deliberate design choice: the session state lives in `~/.local/share/zero/sessions/`, completely separate from the binary. The upgrade only swaps the executable.
