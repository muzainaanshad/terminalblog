**AmpCode dropped a security update on October 22** that doesn't add features — it *removes* trust. Specifically, trust in **eMudhra (emSign) certificate authorities**.

If your MCP servers, proxies, or any infrastructure your agent talks to uses an emSign certificate, **your Amp CLI will now reject the connection** with an "untrusted certificate" error.

This isn't a bug. It's a deliberate supply-chain hardening move. Here's what happened, why it matters, and what to do.

---

## The One-Line Summary

**AmpCode v0.0.1792627309-g98c009+ removes trust in eMudhra/emSign CAs. If your MCP server uses an emSign cert, connections fail. Ask the operator to reissue with a different CA. Run `amp update` now.**

---

## What Happened

On **October 22, 2026**, AmpCode published a security update stating:

> "This update removes trust in compromised certificate authorities, along with other security-related updates. If you see a new 'untrusted certificate' error in the Amp CLI when connecting to a server that uses an eMudhra (emSign) certificate, such as an MCP server or proxy, ask the server's operator to switch to a certificate from another certificate authority."

**Translation:** eMudhra (operating as emSign) suffered a compromise. AmpCode responded by removing their root certificates from the trust store. Any server presenting an emSign-issued certificate is now rejected.

---

## Why This Matters for Coding Agents

Your coding agent makes **hundreds of authenticated network calls per session**:

- Model API endpoints (Anthropic, OpenAI, OpenRouter, etc.)
- **MCP server connections** — tools, resources, prompts
- GitHub/GitLab API calls
- Package registries (npm, PyPI, Cargo, etc.)
- Private corporate proxies

**Every one of those connections relies on TLS certificate validation.** If a compromised CA is trusted, an attacker could:

1. Issue a fraudulent certificate for `api.anthropic.com` or your MCP server
2. Intercept your agent's traffic (model prompts, code, tokens, secrets)
3. Inject malicious responses or steal credentials

**AmpCode's fix closes this vector at the client level.** Your agent simply won't connect to servers using compromised CAs.

## Immediate Action Required

### 1. Update Your Amp CLI

```bash
amp update
# Verify
amp --version
# Should show 0.0.1792627309-g98c009 or later
```

### 2. Test Your MCP Servers

Run a quick connection test for each MCP server you use:

```bash
# In Amp, try connecting to each MCP server
# Or from command line:
openssl s_client -connect your-mcp-server:port -servername your-mcp-server </dev/null | openssl x509 -noout -issuer
```

**Look for:** `eMudhra` or `emSign` in the issuer field.

### 3. If You See "Untrusted Certificate"

**The error will look like:**
```
Error: certificate verify failed: self signed certificate in certificate chain
# or
Error: unable to get local issuer certificate
# with issuer showing eMudhra/emSign
```

**Fix:** Contact the MCP server operator and ask them to **reissue the certificate from a different CA** (Let's Encrypt, DigiCert, GlobalSign, Sectigo, etc.).

**Do not** disable certificate verification. That defeats the entire security fix.

## For MCP Server Operators

If you run an MCP server that agents connect to:

| Current Cert CA | Action Required |
|-----------------|-----------------|
| **eMudhra / emSign** | **URGENT: Reissue from another CA immediately** |
| Let's Encrypt | No action needed |
| DigiCert / GlobalSign / Sectigo / others | No action needed |
| Self-signed | Already untrusted — use a public CA |

**Quick reissue options:**
- **Let's Encrypt:** Free, automated, 90-day expiry (`certbot` / `acme.sh`)
- **ZeroSSL:** Free, 90-day, ACME-compatible
- **Your cloud provider:** AWS ACM, Google Cloud Certificate Manager, Azure Key Vault

## The Bigger Picture: Agent Supply Chain Security

This update highlights a reality most developers ignore: **your coding agent is a high-value supply chain target.**

| Attack Vector | What's At Risk |
|---------------|----------------|
| Compromised CA → MITM model API | Your prompts, code, tokens, secrets |
| Compromised CA → MITM MCP server | Tool calls, file reads, command execution |
| Compromised CA → MITM GitHub/GitLab | Source code, CI/CD tokens, deploy keys |
| Compromised CA → MITM package registry | Dependency confusion, malicious packages |

**AmpCode's fix is the right model:** Remove trust in compromised CAs at the client, force operators to rotate certificates. It's painful short-term, secure long-term.

Other agent vendors (Claude Code, Codex, OpenCode, Zed) should watch for similar CA trust updates. The October 2026 Node.js/Bun security releases also addressed this — if your agent bundles its own runtime, **update the runtime**.
