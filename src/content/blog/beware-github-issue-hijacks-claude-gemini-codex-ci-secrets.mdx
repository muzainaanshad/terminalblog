A security researcher opens a GitHub issue. The title contains a carefully crafted sentence. An AI coding agent picks it up, processes it, and suddenly your `GITHUB_TOKEN`, Anthropic API key, and npm publication token are sitting on an attacker's server.

This is not theoretical. This is what Novee Security demonstrated at Black Hat USA 2026 against the three most widely used AI coding agents: **Claude Code**, **Gemini CLI**, and **OpenAI Codex**.

Two CVEs were assigned. One vendor refused to call it a vulnerability.

If you run any AI-powered GitHub Actions workflow, your blast radius just got a lot bigger.

## The Common Pattern: Untrusted Input → AI Agent → Command Execution → Secret Exfiltration

Every major AI coding agent now offers a GitHub Action that lets the agent respond to issues, review PRs, or triage bugs automatically. The pattern is seductive: drop in a workflow file, grant the agent `Bash` and `Write` access, and watch it handle your backlog.

The problem: **these workflows interpolate unsanitized user-controlled content directly into the agent's prompt.**

| Trigger | User Controls | Interpolated As |
|---------|---------------|-----------------|
| Issue opened | Title, body | `${{ github.event.issue.title }}`, `${{ github.event.issue.body }}` |
| PR opened | Title, body, commits | `${{ github.event.pull_request.title }}`, `${{ github.event.pull_request.body }}` |
| Comment | Body | `${{ github.event.comment.body }}` |
| Push | Commit messages | `${{ github.event.head_commit.message }}` |

No sanitization. No escaping. No delimiter. The attacker's text becomes the agent's instructions.

## Claude Code: Three Rounds of Patch and Bypass (CVE-2026-54316)

Anthropic's `claude-code-action` went through **three distinct vulnerability rounds** during Novee's engagement.

### Round 1: The Quote-Stripping Bypass
Claude Code's command validator stripped single-quoted text before running its 23 validation checks. A payload inside `git push --receive-pack='malicious-payload'` reached the runner untouched. **Remote code execution on the CI runner.** Access to `GITHUB_TOKEN`, Anthropic API keys, any repository secret.

### Round 2: The "Read-Only" Command Exemption
Commands like `tac`, `rev`, `fold`, `expand`, `unexpand` were classified as "read-only" and bypassed path validation entirely. Attackers used `tac` with empty-quote obfuscation to read `/etc/environ` — a file the validator explicitly tried to protect.

### Round 3: The Hugging Face Download Counter Exfiltration Channel (CVE-2026-54316)
This is the one that got a CVE. Claude Code had pre-approved outbound access to Hugging Face via its `WebFetch` tool. The attacker instructed Claude to create up to 64 model repositories — one per possible character of an API key — then monitored public download counters as an encoding channel. **Increment the counter for the repo matching the next character = leak that character.**

| Detail | Value |
|--------|-------|
| CVE | CVE-2026-54316 |
| Affected versions | claude-code-action 0.2.54 – 2.1.162 |
| Fixed in | 2.1.163 |
| Anthropic CVSS v4 | 6.0 (Moderate) |
| NVD CVSS v3.1 | 9.1 (Critical) |

**The score divergence matters:** Anthropic discounts the precondition (getting untrusted content into Claude's context). NVD does not. If your workflow accepts issues from strangers, the precondition is already met.

## Gemini CLI: CVSS 10.0 — Maximum Severity (CVE-2026-12537)

Google's `gemini-cli` and `run-gemini-cli` GitHub Action had a **perfect storm**:

1. **Automatic workspace trust in headless mode** — loaded `.env` files without prompting
2. **Tool allowlist checked at registration, never enforced at runtime** — the agent could call any tool regardless of configuration
3. **Parent process `/proc` environment leak** — Linux `/proc/<pid>/environ` exposes the parent's environment variables

An attacker opens an issue. The workflow runs. The agent reads `/proc/self/environ` (or its parent's). Your `GITHUB_TOKEN`, `GOOGLE_API_KEY`, `GEMINI_API_KEY`, and every other secret in the runner's environment are exfiltrated.

| Detail | Value |
|--------|-------|
| CVE | CVE-2026-12537 |
| GHSA | GHSA-wpqr-6v78-jr5g |
| CVSS v4 | 10.0 (Maximum) |
| Fixed in | gemini-cli 0.39.1 / 0.40.0-preview.3; run-gemini-cli 0.1.22 |

**This is a zero-click RCE.** No user interaction beyond opening an issue. The workflow auto-triggers. The agent auto-executes. The secrets auto-leak.

## OpenAI Codex: "Intended Behavior," No CVE Assigned

Codex presented a fundamentally different case. OpenAI **declined to treat it as a vulnerability.**

The architecture: CI workflows often run **multiple Codex passes in a single job sharing one checked-out workspace**. The first pass can write to `AGENTS.md` — an instruction file Codex loads from disk and treats as authoritative context on every invocation.

`AGENTS.md` is **not protected** like `.git/`, `.agents/`, or `.codex/` directories.

**The attack:** Pass 1 fails schema validation → triggers Pass 2 → Pass 2 loads attacker-controlled `AGENTS.md` → attacker's instructions become the system prompt for Pass 2.

| Detail | Value |
|--------|-------|
| CVE | None assigned |
| OpenAI classification | Intended sandbox behavior |
| Fix | Workflow-level hardening in `openai/codex` repo only |
| Version fix | None — it's a design pattern, not a bug |

**The implication:** Every organization running multi-pass Codex workflows with shared workspace has this exposure. No advisory exists. No version bump will fix it. You must harden your own workflows.

## The Blast Radius: It's Not Just Your Repository

This research, independently validated by Snyk and the Cloud Security Alliance, identifies a **structural vulnerability class** extending far beyond three tools.

Aikido Security named it **PromptPwnd** and confirmed the same pattern across:
- At least **five Fortune 500 companies**
- Google's own `gemini-cli` repository (patched within 4 days of responsible disclosure)
- Any AI-powered CI/CD workflow interpolating unsanitized user content into an agent prompt

The pattern is simple and devastating:

```
Untrusted GitHub Data (issue title, PR body, comment)
        ↓
AI Agent Processes It (interpolated directly into prompt)
        ↓
Agent Executes Commands (Bash, Write, Edit access granted)
        ↓
Credentials Exfiltrated (via GitHub Actions logs, external callbacks, covert channels)
```

## The Secondary Attack Surface: Your Cache Is a Lateral Movement Path

Clinejection (covered previously on this blog) proved that **GitHub Actions cache is a lateral movement vector**. The low-privilege triage workflow shared cache scope with the high-privilege nightly publish workflow. Cache poisoning in the triage job → poisoned `node_modules` restored in the publish job → publication tokens exfiltrated.

**This same cache-sharing pattern exists in most repositories using AI coding agents.** Your "harmless" issue-triage workflow likely shares cache with your release workflow.

## What to Do Today: The Minimal Audit

If you run any AI-powered GitHub Actions workflow, run this audit **now**:

### 1. Search for Unsanitized Interpolation
```bash
grep -r "github.event.issue.title" .github/workflows/
grep -r "github.event.issue.body" .github/workflows/
grep -r "github.event.pull_request.title" .github/workflows/
grep -r "github.event.pull_request.body" .github/workflows/
grep -r "github.event.comment.body" .github/workflows/
grep -r "github.event.head_commit.message" .github/workflows/
```
If any of these appear in a workflow that calls an AI agent — **you have a prompt injection surface.**

### 2. Restrict `allowed_non_write_users`
```yaml
# BAD - anyone with a GitHub account can trigger
allowed_non_write_users: "*"

# BETTER - only collaborators with read access
allowed_non_write_users: "collaborators"

# BEST - only maintainers
allowed_non_write_users: "maintainers"
```

### 3. Remove Shell Access Unless Absolutely Required
```yaml
# If your workflow only labels issues, it does NOT need Bash
allowedTools: "Read,Grep,Glob"  # No Bash, Write, Edit
```
Any `Bash`, `Write`, or `Edit` tool access = code execution capability.

### 4. Separate Cache Scopes by Privilege Level
```yaml
# Low-privilege triage workflow
jobs:
  triage:
    uses: ./.github/workflows/triage.yml
    secrets: inherit
    # Add explicit cache key prefix
    cache-key-prefix: "triage-low-priv-"

# High-privilege publish workflow
jobs:
  publish:
    uses: ./.github/workflows/publish.yml
    secrets: inherit
    cache-key-prefix: "publish-high-priv-"
```
Workflows with different privilege levels **must not share Actions cache scope.**

### 5. Rotate Credentials Thoroughly — Verify Every Token
Cline's incomplete rotation (deleting the wrong npm token) left the exfiltrated token active for **eight more days**. When rotating after a breach:
- Verify **every** token was actually revoked
- Check token scopes — publisher-scoped tokens authorize production releases
- Consider **short-lived credentials** (OIDC provenance for npm) to reduce exposure

### 6. Enable OIDC for Package Publication
Static PATs are an attack surface. OIDC provenance eliminates long-lived tokens. If your publish workflow uses static `NPM_RELEASE_TOKEN`, you are one cache-poisoning incident away from a compromised release.

### 7. Test Your Agent's Approval System
If your coding agent uses regex-based denylists for command approval, test them with shell escape sequences:
- `r\m -rf` (backslash evasion)
- `$(echo rm) -rf` (command substitution)
- `${0/x/r}m -rf` (parameter expansion)
- `rm\x20-rf` (hex encoding)

The patterns that bypass Hermes's `detect_dangerous_command` work against **any regex that doesn't perform proper shell tokenization.**

## The Throughline: Organizational Failures, Not Technical Bugs

Clinejection took **47 days** of private disclosure before public exposure. The fix took **30 minutes** after publication. The credential rotation was **botched**. The unauthorized package was live for **eight hours**.

Every one of those failures is **organizational, not technical**.

The vulnerability classes — prompt injection, cache poisoning, credential scope, covert channels — have been known for years. What's new is that **an AI agent is now the mechanism that composes them into a weapon.**

An agent with `Bash` access reading an unsanitized issue title is the same vulnerability class as a web application concatenating user input into a SQL query. We fixed that in web frameworks **twenty years ago**. The CI/CD ecosystem has not caught up.

## The Good News: Defenses Are Straightforward

1. **Sanitize input** — never interpolate untrusted GitHub data into agent prompts
2. **Scope credentials** — least privilege, short-lived, OIDC where possible
3. **Separate cache** — different privilege levels = different cache scopes
4. **Fail closed** — approval systems must default to deny, not allow
5. **Audit regularly** — the window between disclosure and exploitation is now measured in **days, not months**
