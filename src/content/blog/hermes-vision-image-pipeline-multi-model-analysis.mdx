Vision is one of the hardest problems in autonomous AI. Screenshots, diagrams, UI mockups, whiteboard photos — each type of image is best handled by a different model. Hermes Agent's **vision pipeline** handles this diversity automatically, routing every image to the optimal model without user intervention.

## Multi-Model Vision Routing

When Hermes encounters an image, it routes it to the **best-fit vision model** based on image type, resolution demands, context requirements, and speed needs:

```javascript
const analysis = await agent.analyzeImage({
  image: "/screenshots/bug-report.png",
  question: "What error is shown in the UI?",
});
```

The agent picks the model, not the user. The routing logic evaluates:

| Image Type | Preferred Model | Rationale |
|------------|-----------------|-----------|
| Screenshots (UI bugs, error messages) | GPT-5.6 Vision / Claude Fable 5 | High text extraction accuracy, fast on small images |
| Architecture diagrams | GPT-5.6 Vision | Best at structured diagram parsing |
| Whiteboard photos | GPT-5.6 Vision / Gemini 2.5 Pro | Handles messy handwriting and low contrast |
| Document scans / OCR | Local Tesseract + GPT-5.6 refinement | Privacy-first for sensitive docs, cloud for polish |
| Large context images (>2MP) | Local models (LLaVA, Qwen2-VL) | Avoid cloud token costs, keep data local |

### Routing Algorithm

The pipeline scores each available provider against the image characteristics:

```typescript
interface VisionRoutingScore {
  provider: string;
  model: string;
  score: number;        // 0-100 composite
  latencyEstimate: number; // ms
  costEstimate: number;    // USD per image
  privacyLevel: 'local' | 'cloud' | 'hybrid';
}
```

Factors weighed: **text density** (OCR need), **spatial complexity** (diagram vs photo), **privacy tags** (user-set sensitivity), **budget mode** (cost ceiling), and **latency budget** (interactive vs batch).

## Automatic Provider Detection

The pipeline includes an **auto-detect** mode that reads each provider's vision capabilities from configuration. If a provider supports vision, the pipeline knows. If it doesn't, vision tasks won't route to it. This extends to custom endpoints — add any OpenAI-compatible vision provider and the pipeline probes its capabilities automatically.

### Provider Capability Profile

Each provider registers a capability profile at startup:

```json
{
  "provider": "openai",
  "visionModels": ["gpt-5.6-vision", "gpt-5-vision"],
  "maxImageSize": "20MB",
  "supportedFormats": ["png", "jpeg", "webp", "gif"],
  "maxImagesPerRequest": 10,
  "supportsStreaming": true,
  "supportsLocalProcessing": false,
  "costPerMegapixel": 0.0012
}
```

The gateway polls `/models` on custom OpenAI-compatible endpoints and caches vision support for 24 hours. This means adding a local Ollama endpoint with LLaVA automatically enables local vision routing — no config changes.

## Local Input Credential Safety

When an image is processed locally, the pipeline ensures image data never touches a cloud provider's network, local handlers never access cloud credentials, and the credential guard applies even for local vision models. Recent commits hardened this further by routing all local image inputs through the **shared read guard**.

### The Credential Guard Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                    VISION PIPELINE                          │
├─────────────────────────────────────────────────────────────┤
│  User Input (screenshot, file path, clipboard, URL)        │
│                          │                                  │
│                          ▼                                  │
│  ┌─────────────────────────────────────────────────────┐   │
│  │           SHARED READ GUARD                         │   │
│  │  • Validates path is within allowed directories     │   │
│  │  • Strips EXIF/metadata unless explicitly kept      │   │
│  │  • Enforces max file size (configurable, default 20MB)│ │
│  │  • Hashes image for deduplication cache             │   │
│  └─────────────────────────────────────────────────────┘   │
│                          │                                  │
│          ┌───────────────┴───────────────┐                 │
│          ▼                               ▼                 │
│  ┌───────────────┐               ┌───────────────┐        │
│  │  LOCAL PATH   │               │  CLOUD PATH   │        │
│  │               │               │               │        │
│  │ • LLaVA       │               │ • GPT-5.6     │        │
│  │ • Qwen2-VL    │               │ • Claude 5    │        │
│  │ • Ollama      │               │ • Gemini 2.5  │        │
│  │               │               │               │        │
│  │ Credentials:  │               │ Credentials:  │        │
│  │    NEVER      │               │    SCOPED TO  │        │
│  │    ACCESS     │               │    PROVIDER   │        │
│  └───────────────┘               └───────────────┘        │
└─────────────────────────────────────────────────────────────┘
```

The **shared read guard** (introduced in v0.20.1) is the single choke point — all image reads, whether from disk, clipboard, or HTTP, pass through it. This eliminates the class of bugs where a local image handler accidentally picked up cloud credentials from environment variables.

## The Image Generation Pipeline

Beyond analysis, Hermes supports image generation across providers — FLUX for high-quality art, SDXL/DALL-E for photorealism, local models for private generation. Each provider has its own capability profile and the pipeline routes accordingly.

### Generation Routing Table

| Use Case | Model | Provider | Local Option |
|----------|-------|----------|--------------|
| UI mockups from description | FLUX.1 [pro] | Replicate / Fal.ai | ComfyUI + FLUX |
| Architecture diagrams | GPT-Image / DALL-E 3 | OpenAI | SDXL + ControlNet |
| Code diagram generation | Mermaid.js → render | Local (no model) | Built-in |
| Icon/asset generation | FLUX.1 [dev] | Local | ComfyUI |
| Photo-realistic scenes | DALL-E 3 / Midjourney | OpenAI / Discord | SDXL |

Generation requests flow through the same credential guard — API keys never leave the provider-scoped vault.

## Real-World Vision Workflows

### 1. Bug Report Analysis — Screenshot to Fix

```bash
# User pastes screenshot in terminal
/hermes analyze /tmp/bug-report.png "Find the root cause"
```

Pipeline steps:
1. Read guard validates `/tmp/bug-report.png` (safe path, <20MB, PNG)
2. Image classified: "error screenshot, high text density"
3. Router selects: GPT-5.6 Vision (cloud) — best OCR on small UI text
4. Prompt constructed with system context: "You are a debugging assistant. Extract error, stack trace, UI state. Suggest likely file locations."
5. Response parsed → codebase search triggered automatically
6. Results aggregated: error + 3 candidate files + suggested fix

**Time saved**: ~15 min manual description → 30 sec autonomous.

### 2. UI Diff Comparison — Visual Regression Detection

```bash
/hermes compare /screenshots/before.png /screenshots/after.png "What changed visually?"
```

Pipeline:
1. Both images read through guard, hashed for cache
2. Classified: "UI screenshots, low text, high spatial detail"
3. Router: GPT-5.6 Vision (handles multi-image comparison natively)
4. Prompt: "Compare pixel-by-pixel. List added/removed/modified elements. Ignore dynamic content (timestamps, ads)."
5. Output: structured diff — "Button moved 12px right, color changed #0066cc→#0052a3, new toast container added"

Integrates with CI: run on PR screenshots, fail if unexpected visual changes.

### 3. Diagram Understanding — Architecture to Code

```bash
/hermes diagram /docs/architecture.png "Generate the service interface definitions"
```

Pipeline:
1. Image classified: "structured diagram, boxes/arrows, labels"
2. Router: GPT-5.6 Vision (best at diagram semantics)
3. Multi-pass extraction:
   - Pass 1: Identify components, relationships, protocols
   - Pass 2: Extract method signatures, data flows
   - Pass 3: Generate TypeScript interfaces + Mermaid diagram
4. Output: ready-to-commit interface files + updated architecture doc

### 4. Document OCR — Scanned Papers to Searchable Context

```bash
/hermes ocr /scans/meeting-notes.pdf "Extract action items and decisions"
```

Pipeline:
1. PDF → image pages via poppler (local, no cloud)
2. Each page: Tesseract OCR (local, fast, private)
3. Raw OCR text → GPT-5.6 for structure recovery (headers, tables, lists)
4. Final pass: extract entities (dates, people, tasks, decisions)
5. Output: structured markdown + JSON for task tracker import

**Privacy**: Sensitive documents never leave machine — local Tesseract + local LLaVA option for full air-gap.

## Advanced: Multi-Image Sequences

Hermes handles image sequences (video frames, scroll captures, multi-page docs) as a single analytical unit:

```javascript
const analysis = await agent.analyzeImageSequence({
  images: [
    "/scrolls/login-flow-1.png",
    "/scrolls/login-flow-2.png",
    "/scrolls/login-flow-3.png"
  ],
  question: "Trace the authentication flow end-to-end"
});
```

The pipeline:
- Detects sequence via naming/timestamp metadata
- Uses **context-aware routing**: first image picks model, rest use same for consistency
- Aggregates cross-image references ("the button on step 1 becomes the form on step 2")
- Outputs unified narrative + annotated sequence

## Performance Characteristics

| Scenario | Model | Latency (p50) | Cost/Image | Privacy |
|----------|-------|---------------|------------|---------|
| Single screenshot (bug) | GPT-5.6 Vision | 1.2s | $0.003 | Cloud |
| Single screenshot (bug) | LLaVA-1.6 (local) | 3.8s | $0.000 | Local |
| Diagram (complex) | GPT-5.6 Vision | 2.1s | $0.005 | Cloud |
| 10-page PDF OCR | Tesseract + LLaVA | 12s | $0.000 | Local |
| 5-image UI diff | GPT-5.6 Vision | 4.5s | $0.015 | Cloud |

**Batch mode**: Queue 50+ images, pipeline processes in parallel (max 3 concurrent cloud, unlimited local), ~80% throughput gain.

## Limitations & Roadmap

**Current limitations:**
- No vision output (can't generate diagrams/mockups natively — uses Mermaid/PlantUML render)
- Video input not supported (extract frames first)
- Max 10 images per request (provider limit)
- Local models slower on CPU-only machines

**v0.21+ roadmap:**
- Video frame extraction + temporal analysis
- Vision output via integrated ComfyUI/SDXL pipeline
- Custom vision skill types (user-defined routing rules)
- Cross-session visual memory (remember diagrams across projects)
