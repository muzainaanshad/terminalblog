This week on Hacker News, a team launched **Kastra** — runtime authorization for AI coding agents. It intercepts tool calls and evaluates them against policies before they execute.

The origin story is what caught my attention:

> "We built Kastra after one of our Cursor agents almost executed DELETE FROM customers WHERE status='test' against a production database."

That sentence should make every developer using coding agents pause.

## The Near Miss

A Cursor agent, working on what was presumably a test task, generated `DELETE FROM customers` and tried to execute it against production. The team caught it before it ran. That's the kind of story that keeps DevOps engineers up at night.

But here's what bothers me: **this story is going to become more common, not less.**

## Why This Is About to Get Worse

Three trends are converging:

1. **Agents are getting more autonomous** — Claude Code, Codex, and Cursor all ship features that let agents do more without human approval. The whole industry is racing toward "delegate and forget."

2. **Database access is getting easier** — Every coding agent can now connect to databases directly. Cursor has database mode. Claude Code runs SQL through bash. Codex has native DB tools.

3. **Production vs staging boundaries are blurring** — When agents set up infrastructure, they often create staging and production in the same session. The boundary between them is a variable name — easy to get wrong.

## What Kastra Gets Right

Kastra's approach — intercept tool calls before they execute and check them against deterministic policies — is the right architecture for agent security. It's similar to how AWS IAM works: deny by default, allow explicitly.

Their stated support for Claude Code, Cursor, and Codex covers the three most-used coding agents. That's smart targeting.

## What Kastra Misses

Policies only work if you write them. Most teams don't have database access policies documented. Most teams don't know what their agents should and shouldn't touch.

The tool is a solution to a problem that most teams haven't admitted they have yet. And by the time they do admit it, they'll have already had the near-miss.

## The Real Fix

The best defense against "agent deleted production" isn't a policy engine. It's:
1. **Read-only database users** for development agents
2. **Separate infrastructure** — staging agents should never have production credentials
3. **Human approval gates** on destructive operations — no agent should run DROP or DELETE without confirmation

Kastra can help. But the safety culture matters more than the tool. The team that nearly ran DELETE FROM customers didn't need Kastra — they needed a read-only database user. That's free, it's instant, and it would have prevented the near-miss entirely.
