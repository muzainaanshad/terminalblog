## The Conversation Happening in Plain Sight

Hacker News threads about AI coding agents rarely make headlines, but they're where the actual practitioners — people shipping production code with these tools daily — trade unfiltered observations. No marketing copy. No vendor benchmarks. Just developers describing what happens when the demo ends and the real work begins.

Over the past week, several threads exploded with hundreds of comments each, revealing a consistent picture: the tools are genuinely useful, the mental model shift is harder than advertised, and critical safety gaps remain unresolved.

---

## The "80% Right, 20% Subtly Wrong" Trap

The most striking thread came from a developer using frontier models (Opus 5.5, Astra, Sol 6.1, Fable 5.1, Gemini Argon) who described a sensation "between cognitive dissonance, FOMO, and a vague sense of being gaslit."

Their observation: **AI writes code that's 80% correct and 20% wrong in ways that only deep system knowledge catches.**

> "When I review the code it writes — and this is all of them — 80% of it is right, and 20% is wrong, but in extremely subtle ways; only when you deeply understand the system and carefully review it do you spot the issues. These are not stylistic choices, the code is incorrect."

The concrete example: asked to write an integration test reproducing a production bug, the AI combined two separate backend fakes into a single store protected by one mutex. The code looked clean — reasonable function names, good organization — but it **missed the entire concurrency bug** because the real system wrote to both stores concurrently and one write failed.

Even "grill-me skills and cross-model adversarial review" (techniques where you prompt the model to criticize its own output or have different models debate) didn't catch it.

### What this means for you

If you're new to AI coding agents, the trap is trusting the **appearance** of correctness. The code compiles, passes basic tests, and follows patterns. But semantic correctness — does this actually solve the problem in the real system context? — still requires a human who understands the architecture.

**Practical takeaway:** Treat AI output as a sophisticated first draft, not a final artifact. The more complex your system's invariants (concurrency, data consistency, security boundaries), the more review attention those areas need.

## The "Stopped Reading Plans" Phenomenon

A separate Ask HN thread asked: *Do you read your coding agent's plans before approving?*

The responses were revealing:

- **"No. Stopped maybe around 5-6 months ago."** — One developer now just checks the git changelog and asks a side agent "why was this change made?" if something looks off.
- **"I check it through because I can't read the code. Then test it. Then regression test it."** — Another admits they can't effectively review the code itself, so they verify behavior instead.
- **Prompting has devolved to "caveman/idiot" style** — Positive reinforcement for preferred patterns, minimal instruction, skip the planning phase entirely.

### The shift: from review to verification

Early adopters treated AI like a junior dev — read the plan, review the code, approve. Experienced users have moved to **behavioral verification**: run the tests, check the diff, ship if it works.

This isn't necessarily irresponsible. It reflects a hard-won realization: **reading AI-generated plans doesn't reliably catch the subtle semantic errors** (see above). The plan looks logical; the code looks clean; the bug is in the mismatch between the model's mental model and your actual system.

### What this means for you

If you're starting out, **read the plans**. You're building the mental model of what the agent can and can't do. But expect to graduate to "trust but verify via tests" as you learn the failure modes.

Don't feel guilty about skimming plans once you've seen enough patterns. The industry is converging on: *write good tests, let the agent iterate until they pass, then do a focused diff review on critical paths.*

## Security: The "Don't Ask Again" Secret Leak (410+ Comments)

**This week's biggest story:** Security firm Apiiro scanned public GitHub repos for `.claude/settings.json` and `.claude/settings.local.json` files. They found **1,122 repos containing actual secrets** — database passwords, API keys, cloud credentials — all sitting in plain text because developers clicked "Don't Ask Again" on permission prompts.

### How it works (and fails)

When Claude Code asks permission to run a command containing a secret (like `curl -H "Authorization: Bearer sk_live_..."`), clicking "Don't Ask Again" stores that **entire command string — secret included** — in a local settings file. 

Claude Code adds this file to your *global* gitignore, but **not the repo's `.gitignore`**. Clone the repo on a new machine, or let Claude commit the file itself (which happened in **539 of the 1,105 traced repos**), and the secret goes public.

### Developer reactions split sharply

**Camp A: Blame the developer.**
> "Devs have been leaking secrets in public repos a long time before now. Nothing new here, except there are now more with dev power, which statistically means more leakage."
> "Review your code before committing. Do code reviews on PRs."
> "Basic security hygiene means you use password manager CLI, SSH agent, at worst temporary git-ignored env files, so that the secrets would never appear in the command line and you would never pass them to Claude."

**Camp B: The tool design enables the mistake.**
> "The root issue is not the button, it is that the allowlist stores the full command string, including whatever was in it. We ran into this ourselves: approve `curl -H \"Authorization: Bearer ***` once and that token sits in settings.local.json until someone happens to reread the file."
> "Claude Code didn't publish these secrets, the users did by committing their Claude Code settings to public repos. Same thing could/would happen with an open source harness."

**The uncomfortable middle:** Several commenters admitted they'd done exactly this — clicked "Don't Ask Again" on a command with a token, forgot about it, and only caught it because a secret scanner flagged it later. The feature *works as designed*; the design just doesn't match how humans actually behave.

### What this means for you

**Don't click "Don't Ask Again" on commands with secrets.** Ever. Use environment variables. Use a secret manager (1Password CLI, Doppler, Infisical). Run `gitleaks` as a pre-commit hook — it's saved people "so many times."

**Better designs exist** (and the industry needs to adopt them):
- Store only command *patterns* (hash the secret portions)
- Require secrets to come from environment variables, never inline
- Auto-rotate secrets detected in approval history
- Sandbox the agent from the host filesystem entirely

## Enterprise Adoption: Goldman Sachs Bans Local Agents (421+ Comments)

Goldman Sachs restricted Claude Code access for its bankers and traders in Hong Kong. Their ~12,000 engineers keep access, but the front-office staff — the people building "vibe-coded" tools to analyze trades, summarize emails, and automate workflows — got cut off.

### The stated reason: a "lethal trifecta"

Semi-unattended agents running on workstations with access to:
1. Client data / trading systems
2. Email / internal communications  
3. The public internet

One prompt injection or mistake away from a major leak.

### Developer reactions reveal the real enterprise gap

**The "banks know what they're doing" camp:**
> "Banks and financial firms have been super careful about this stuff since well before the AI era." (referencing 1980s NASD rules requiring dedicated trading PCs)
> "The agent should *not* be running on the same workstation. It should have a hard isolation barrier between it and the host machine. We shouldn't be starting from a fail-unsafe state and then trying to patch in security."

**The "this kills productivity" camp:**
> "There's no edge in using the same tools that everyone else is using, especially in markets/finance. Let your competition all melt their brains, maybe only give employees you know are actual super contributors unlimited access to LLMs."
> "Claude is great at running scenarios. I think gs traders will be behind the other traders without these tools."

**The "vibe coding isn't engineering" perspective:**
> "You have to go all in on agentic engineering. And if you're all in on agentic engineering and doing it well, then anyone should be able to build safely and no one needs to look at the code."
> "At which point it's vibe coding, not engineering."
> "Giving a coding tool to a non engineer is like giving a chainsaw to a 5 year old. You just don't do that."

### The pattern that works: sandboxed agents + API proxies

Commenters who've solved this internally describe the same architecture:
- **Ephemeral VMs or cloud workspaces** per task
- **API proxies** that mediate every external call (read allowed, write requires human confirmation)
- **Zero secrets passed to the agent** — the proxy injects them at runtime
- **Network segmentation** so the agent can't reach internal systems directly

This isn't "Claude Code with guardrails." It's a **different deployment model entirely**. The current local-agent paradigm fundamentally conflicts with regulated environments.

### What this means for you

**If you're leading a team:** Ban local agents on machines with production access. Full stop. Use sandboxed environments. The "lethal trifecta" is real.

**Invest in the proxy layer.** The teams successfully using agents at scale built API gateways that mediate every external call. The agent asks; the gateway enforces policy. This is the only model that survives audit.

**Define "agent-ready" codebases.** Explicit allowlists for what the agent can touch. Autonomy levels per directory (billing = human approval required, tests = agent can run freely). This is what tools like Airlock and Sentient are building toward.

## Skill Atrophy: "I'm Losing the Ability to Write Code" (Ask HN)

A 12-year veteran posted:
> "I have been working as software engineers for 12 years, and the last 2 years I have been utilize AI for coding, and the last years mostly I don't code or type code anymore, just doing prompt, a review of the generated code, and setting a workflow for agent to spesific task. I just feels I'm starting to lose my basic programming skills to write code from scrath"

The responses were telling:

> "I think it's starting to become the new normal. A couple of years ago I was pushing myself to go way out of my way to use AI code assistants in tasks I would never use before. Now I find myself doing the exact same thing but to manually write code."

> "Actually, it seems like the reason to type the code directly has disappeared. In Korea, the computer science field is already experiencing a shortage of new university students, and developers' salaries have been cut by an average of 50%."

> "Writing is not merely the final product of thought; it is the primary tool through which thinking happens. Reading the diff after the LLM writes the code 'feels' like understanding but I don't think it really is. If you didn't write the code, did you write the spec, the tests, or the design? If not, who did the thinking?"

> "If you enjoy coding, keep doing it. If it's only something you do for a paycheck then do whatever the paycheck requires, let AI write it all. If you're worried about losing your skills, the obvious solution is to just keep writing code, for yourself."

### The uncomfortable reality

The veteran losing his ability to write from scratch isn't an outlier. He's the **early indicator**. The Korean salary data (50% cuts) and CS enrollment collapse suggest the market is already pricing "prompt operator" differently than "software engineer."

The core question: **if you don't write code, do you still understand the system?** Reading diffs feels like understanding. It isn't. When the agent produces a subtle bug in a distributed system — a race condition, a consistency violation, a performance regression that only shows at scale — the "reviewer" who never built the mental model from scratch often misses it.

### What this means for you

**Keep writing code by hand.** Not for the output — for the *thinking*. Build side projects without AI. Do the Advent of Code. Implement a data structure from scratch. The mental model you build is what lets you review AI output effectively.

**Treat the agent as a junior pair programmer, not a senior architect.** It writes boilerplate well. It designs systems poorly. You still own the architecture.

**If you're leading a team:** Plan for skill maintenance. If your seniors stop writing code, they stop being effective reviewers. Rotate people off AI-assisted work periodically. Make "write it yourself" a deliberate practice, not a nostalgic hobby.

## Open-Weight Alternatives: The Terminology Trap

Another thread asked for "open-weight alternatives to Claude Code" — and immediately exposed widespread confusion.

**Claude Code is a harness (CLI tool), not a model.** It runs Anthropic's closed models (Opus, Sonnet) on their servers. You can't self-host it.

What people actually want falls into three buckets:

| What you're asking for | What you actually need |
|------------------------|------------------------|
| Open-weight **model** to replace Opus/Sonnet | GLM-5.x, Kimi 3.x, DeepSeek Flash (via OpenRouter or local) |
| Open-source **harness** to replace Claude Code CLI | OpenCode, OpenHands, Aider, Goose |
| Both, running locally | Significant hardware ($20K–40K for DGX/Halo-class) |

**Most practical recommendation:** **OpenCode + OpenRouter**. OpenCode is an open-source harness; OpenRouter gives you access to dozens of models (including open-weight ones) with a single API key. You can even point OpenCode at your Anthropic account *if* you have API access (subscription plans are locked to Claude Code).

**DeepSeek Harness** was also mentioned as viable — DeepSeek Flash is "pretty competent" and open-weight, though buying tokens from DeepSeek is cheaper than self-hosting.

### What this means for you

Don't conflate the **interface** (harness) with the **intelligence** (model). You can mix and match:
- Use OpenCode (harness) + Anthropic API (model) = Claude Code experience, your own billing
- Use OpenCode + OpenRouter + DeepSeek Flash = fully open-weight stack
- Use Aider + local Ollama = fully offline, but model quality caps at what your GPU runs

Start with OpenCode + OpenRouter. It's the lowest-friction way to experiment with model switching without changing your workflow.

## Hardware Economics: AI Tools Are Changing Upgrade Decisions

"Ask HN: Are you putting off hardware upgrades because of AI coding tools?" drew opposing camps:

**Camp A (putting off upgrades):** Hardware is 3.5x more expensive than two years ago. Memory and SSD prices haven't normalized. Why buy when cloud agents do the heavy lifting?

**Camp B (upgrading anyway):** Cloud coding agents run on "shitty VMs (no GPU)." Local work melts laptops when running multiple agents. The more you use these tools, the more you hit local compute limits.

> "The more I can do with coding agents the more I am getting limited: cloud coding agents are running on shitty VMs (no GPU), my laptop is melting down whenever I try to do a few more things at once."

### What this means for you

If you're doing serious agent work (multiple concurrent sessions, large codebases, compile/test loops), **local GPU memory becomes the bottleneck.** Cloud offloads model inference but not the surrounding toolchain — file ops, builds, tests, language servers all run on your machine.

Practical minimum for a smooth experience in late 2026:
- 64 GB RAM (32 GB is painful with multiple agents + browser + IDE)
- 2 TB NVMe (agent workspaces + caches + container images add up)
- If self-hosting models: 24 GB+ VRAM (single 3090/4090) for 7B–14B models; 48 GB+ for 32B+

Don't upgrade *for* AI tools. Upgrade when your current machine becomes the limiting factor in your iteration speed.

## Security: The Supply Chain Problem Nobody Talks About

A Microsoft security blog postmortem detailed a **malicious Cursor extension branded as "Claude Code"** that installed a persistent SSH backdoor. It sat in the marketplace, accumulated installs, and exfiltrated credentials.

The HN comment was brief: just a link to the archive.is snapshot. But the implication is loud: **the agent ecosystem is a supply chain attack surface.**

Every extension, MCP server, harness plugin, and model router is code running with your repository access. The "vibe coding" workflow — install tool, point at repo, go — skips the vetting steps traditional dependencies get.

### What this means for you

- Audit extensions before installing. Check the publisher, read the source if it's open.
- Treat MCP servers as third-party code with filesystem/network access.
- Use separate GitHub tokens with minimal scopes for each tool.
- Run agents in containers/VMs when experimenting with new tools.

## The Real Insight: Three Tensions Nobody Has Resolved

### 1. Convenience vs. Safety Is a False Dichotomy — The Tooling Is Just Immature

The "Don't Ask Again" leak isn't a user education problem. It's a *design* problem. Storing approved commands verbatim — secrets and all — in a file that's easy to accidentally commit is a choice. Better designs exist (see above). But these require engineering investment. Right now, the industry is shipping "works on my machine" convenience and calling it a product.

### 2. Enterprise Adoption Requires a Different Architecture, Not Just Policy

Goldman didn't ban AI. They banned *local* AI agents with unfettered access to sensitive environments. The teams who've solved this built: ephemeral VMs, API proxies, zero-secret injection, network segmentation. This is a **different deployment model**, not a configuration toggle.

### 3. Skill Atrophy Is Real, But the Industry Is Pretending It Isn't

The veteran losing his ability to write from scratch is the canary. The market is already pricing "prompt operator" differently. The uncomfortable question remains: **if you don't write code, do you still understand the system well enough to catch the subtle 20%?**

| Stage | Focus | Skip |
|-------|-------|------|
| **Week 1–2** | Read plans. Compare outputs across 2–3 models (OpenCode + OpenRouter makes this easy). Learn failure patterns. | Optimizing prompts, buying hardware, self-hosting models |
| **Month 1** | Build a test suite that exercises your system's tricky invariants (concurrency, auth, data flow). Let the agent iterate until tests pass. | Comprehensive plan review, perfect prompts |
| **Month 2+** | Identify your actual bottlenecks: model quality? context window? local build speed? Upgrade *that*. | Chasing every new model release |

**Security basics from day one:**
- Never click "Don't Ask Again" on commands with secrets
- Use environment variables + secret manager (1Password CLI, Doppler)
- Run `gitleaks` as pre-commit hook
