## What Happened

Last week, security firm Apiiro published research showing that **Claude Code's "Don't Ask Again" permission feature had leaked secrets in 1,122 public GitHub repositories**. The mechanism: when you approve a command with "Don't Ask Again," Claude Code saves that exact command — including any passwords, API keys, or tokens you typed — into a local settings file (`.claude/settings.local.json`). 

Here's the kicker: **Claude Code only adds this file to your *global* gitignore, not the repository's `.gitignore`**. So when you clone the repo on a new machine, or when Claude itself commits changes (which happened in 539 of the 1,105 repos traced), those secrets get committed and pushed to GitHub.

The story hit Hacker News and exploded to **292 comments** — a rare signal-to-noise ratio for a security story. Developers didn't just share outrage; they dissected the failure modes, argued about responsibility, and shared actual mitigation strategies.

## Developer Reactions: The Blame Game

### "It's User Error, Not a Bug"

The dominant sentiment: **this is a PEBKAC (Problem Exists Between Keyboard And Chair) issue**.

> "According to Claude docs, settings.local.json isn't to be committed. This is just people being the usual sloppy with secrets in repos, not something particular to Claude or AI in general." — *skeledrew*

> "People chose to upload a file containing their password and make it publicly accessible, I don't see a problem here." — *GaryBluto*

> "Plain text secrets? Super rookie mistake!" — *mococa*

Several commenters noted that developers have been committing `.env` files, SSH keys, and AWS credentials to public repos long before AI agents existed. The agent just automated the foot-gun.

### "The Tool Should Prevent This"

A strong minority disagreed: **the UX design actively encourages the mistake**.

> "The file is created inside the project, and Claude Code only adds it to your global git ignore, not the repo's .gitignore. So a fresh clone or a second machine commits it like any other file." — *shmulc (article author)*

> "In 539 of the 1,105 repos we traced, a commit co-authored by Claude itself changed the file." — *shmulc*

This is the critical detail: **Claude Code committed the secrets itself in nearly half the affected repos**. The agent that leaked the secret also committed the leak.

### "Vibe Coders Don't Know Git"

A recurring theme: **AI has brought a wave of developers who don't understand version control**.

> "They're probably mostly just random solo people who barely even know what git is. This — that people who don't know how to code can code now — is the whole thing that AI companies love to advertise, and it's true. But it also means that tools need to stop people from doing stupid things, because they won't know that the things they are doing are stupid." — *pastel8739*

> "The new wave of git users (coming from AI) don't know what git is." — *hathawsh*

> "I've set a hard rule for my agents to 'never add all files, never commit all files, always reference the specific files you are adding or committing.' They violate it so regularly that my 'git' command is now a wrapper, when the agent fucks up and tries to add/commit-all anyway, it now gets a nastygram error chiding it for not following instructions." — *cobbzilla*

## The Real Insight: Three Failure Modes

Reading through 292 comments, three distinct failure modes emerge — only one is purely user error.

### 1. The Global vs. Repo Gitignore Mismatch (Design Flaw)

Claude Code adds `.claude/settings.local.json` to your *global* `~/.gitignore`. But global gitignores **don't travel with the repo**. Anyone cloning your repo — including CI/CD, your future self on a new laptop, or a contributor — has no protection.

> "A fresh clone wouldn't have the file. This claim doesn't make any sense. The only way I can see this getting committed is if someone edited their global .gitignore or, more likely, did a whole directory transfer to a different machine to work on." — *Aurornis*

> "Fair, 'fresh clone' was wrong. It happens on a new machine or container without the global ignore, in a copied project folder, or once the file has been committed, since ignore rules don't apply to tracked files." — *Aurornis (corrected)*

**The fix is trivial**: also write to the repo's `.gitinfo/exclude` or `.gitignore`. Anthropic hasn't done this yet.

### 2. Agent Commits Its Own Leaks (Automation Failure)

In 539 repos, **Claude Code itself committed the settings file containing secrets**. The agent was given permission to run git commands, saw a changed file, and committed it — secrets and all.

> "I've set a hard rule for my agents to 'never add all files, never commit all files, always reference the specific files you are adding or committing.' They violate it so regularly that my 'git' command is now a wrapper..." — *cobbzilla*

Developers are now **wrapping `git` in custom scripts** that reject `git add .` or `git commit -a` from agents. This is the world we live in: you have to adversarially harden your own toolchain against your assistant.

### 3. Secrets on the Command Line (Workflow Failure)

The root cause: **developers typing secrets directly into shell commands** that Claude then executes and saves.

> "At the same time, I want them to take away the tedium of a bunch of tasks I'm required to do, and it sucks to have to micromanage them. The best solution I've been able to come up is using an ephemeral VM per task, using --dangerously-skip-permissions so it doesn't bother me. I couple that with an API proxy that lets me restrict the permissions it has to external services." — *tsergiu*

> "I keep all my creds in a password manager (1Password in my case) and Claude can't see them — when a cred is needed it runs a script that calls the op CLI and I tap my fingerprint for access." — *binarymax*

> "I always have it write a script and then write the secret to a different file myself, then instruct the agent to use the secret file in the script. That way the secret never goes through an external entity." — *ohyes*

## What Developers Actually Do: Mitigation Strategies

The comment thread is a goldmine of **battle-tested patterns**. Here's what experienced operators actually do:

### Pattern 1: Never Give Agents Raw Secrets

| Approach | Tools Mentioned |
|----------|-----------------|
| Password manager CLI + script wrapper | 1Password (`op`), Bitwarden (`bw`), `pass` |
| Secret injection via env files (gitignored) | `.env.local`, `direnv` |
| Dedicated secret manager for agents | Infisical, Doppler, HashiCorp Vault, `agent-vault` |
| API proxy with scoped permissions | Custom proxies, `keycontain.com` |

### Pattern 2: Sandbox Everything

> "I run EVERYTHING inside MicroVMs with LimaVM. Employer pays for Claude Code, which I run inside lima with herdr... For secrets protection I run `agent-vault` so claude does not have access to API keys/secrets. I try not to run any npm/cargo/ruby stuff on my machine, but run everything from the vm. If (when) the VM will get compromised, I just wipe it off, and restart from scratch." — *skwee357*

> "I just mount .git read-only in my sandbox. That way I don't need to worry about it violating my safeguards." — *grepular*

### Pattern 3: Pre-Commit Hooks Are Non-Negotiable

> "This is why you ALWAYS run gitleaks as a pre-commit hook, agent or not. It's saved me from myself so many times." — *nunez*

> "If you really need to commit private files to GitHub, use Turbocrypt or git-crypt." — *jedisct1, Groxx*

### Pattern 4: Separate Dev and Release Repos

> "Use a private dev repo and do all your dev inside it. Releases go to a separate public repo. In the private dev repo use a script which cherry-picks release files from a whitelist that you maintain in the public repo." — *tim-projects*

## What It Means For You

### If You're New to AI Coding Agents

**You are the target demographic for this leak.** The "vibe coding" marketing tells you the agent handles everything. It doesn't handle opsec.

1. **Never type a secret into a terminal an agent controls.** Use a password manager CLI or env files.
2. **Add `.claude/` to your repo's `.gitignore` immediately** — don't rely on global gitignore.
3. **Enable gitleaks/trufflehog as a pre-commit hook** on every repo, today.
4. **Don't use `--dangerously-skip-permissions`** until you understand what it bypasses.

### If You're Running Agents in Production/CI

1. **Mount `.git` read-only** in the agent's environment.
2. **Wrap `git` with a deny-list** for `add .`, `commit -a`, `push --all`.
3. **Use ephemeral environments** (VMs, containers) that die after each task.
4. **Rotate any secret that ever touched an agent's context window** — assume compromise.

### If You're Building Tooling

The market is screaming for:
- **Agent-aware secret managers** (scoped tokens, auto-rotation, audit logs)
- **Git wrappers that enforce commit policies** per-agent
- **Sandbox orchestration** that's simpler than LimaVM + Tailscale + custom scripts
- **Pre-commit hooks that understand agent-generated files**

## The Uncomfortable Truth

> "Devs have been leaking secrets in public repos a long time before now. Nothing new here, except there are now more with dev power, which statistically means more leakage." — *skeledrew*

The leak isn't novel. **The scale is.** AI agents let more people write and commit code faster, with less understanding of the systems underneath. The tooling hasn't caught up to the new user base.

Anthropic's response (from Boris on the Claude Code team): "Historically Claude Code has not done secret scrubbing... but we are looking into what we can do to prevent this. Permission rules are old hat. Everyone should be using auto mode instead."

**Auto mode** (the default) reviews each tool call before execution. It would catch a command containing a secret. But "Don't Ask Again" exists *because* auto mode is slow and verbose for repetitive tasks. Developers disable the guardrail to go faster — and that's exactly when the leak happens.

## TL;DR

| Myth | Reality |
|------|---------|
| "Claude Code leaked my secrets" | You typed secrets into commands; Claude saved them; you (or Claude) committed them |
| "It's a bug" | It's a UX design that assumes git literacy |
| "Auto mode fixes it" | Auto mode is slower; developers disable it for speed |
| "Secret scanning catches it" | Only if you enable it *before* the commit |

**The fix isn't waiting for Anthropic.** It's treating every agent session as a potential secret exfiltration channel — because that's what the data shows it is.
