Writing code is one thing. Opening a PR, getting it reviewed, and landing it is where the real work happens. Hermes Agent's **git workflow integration** automates the entire lifecycle — from branching to merge — without you touching the command line.

## The Full Autonomous PR Lifecycle

Here's what happens when you tell Hermes "fix the memory leak in the auth module":

### 1. Branch Creation

Hermes creates a feature branch with a descriptive name:

```bash
git checkout -b fix/memory-leak-auth-module
```

The branch name follows your project's conventions — automatically detected from your commit history. Hermes analyzes your recent branch naming patterns (e.g., `feat/`, `fix/`, `chore/`, `refactor/`) and applies the same convention.

### 2. Code Changes

The agent plans the fix, reads the relevant files, makes the changes, and verifies them:

- Reads the auth module source and related files
- Identifies the leak pattern (unclosed connections, missing cleanup, resource handles)
- Implements the fix with minimal, focused changes
- Runs the relevant tests (unit, integration, or both)
- Lints the changed files against project standards
- Verifies no regressions in related functionality

### 3. Commit

Commits are structured with conventional commit format:

```
feat(auth): fix unclosed database connections in session handler

Closes unclosed PostgreSQL connections in the session middleware
that caused connection pool exhaustion under load.

The fix adds a finally block to ensure connections are always
returned to the pool, even when an error occurs.
```

No "Update file.js" commits. Each message explains the what and the why. Hermes also supports **commit signing** (GPG/SSH) and **co-authored-by** trails for audit trails.

### 4. PR Creation

Hermes opens a pull request with:

- **Title** that follows your repo's conventions (detected from recent PRs)
- **Description** explaining the problem, the fix, and testing approach
- **Labels** auto-assigned based on change type (bug, enhancement, docs, refactor, etc.)
- **Reviewers** suggested based on git blame ownership and CODEOWNERS
- **Draft/PR status** based on your configuration (ready for review vs. draft)

```markdown
## Problem
Unclosed database connections in the auth session handler
cause connection pool exhaustion after ~100 concurrent logins.

## Fix
Added a try/finally block in SessionManager.refresh()
that always returns the connection to the pool.

## Testing
- Added unit test for connection cleanup on error
- Existing auth tests pass (17/17)
- Manual load test confirms pool stays stable at 50 concurrent

Closes #8472
```

### 5. Post-PR Handling

- Watches for CI status (GitHub Actions, GitLab CI, CircleCI, etc.)
- If checks fail, analyzes the failure and pushes a fix commit
- If reviews request changes, addresses them with follow-up commits
- Marks the PR as ready for human review when all checks pass
- Auto-merges when configured (with required approvals and passing checks)

## The Review Side

Hermes also reviews PRs opened by others. When you tag it:

```
/review https://github.com/org/repo/pull/8472
```

Or configure it as a **required reviewer** in branch protection rules for automatic review on every PR.

It performs a full review inline:

- **Security scan** — checks for common vulnerability patterns (SQL injection, XSS, path traversal, hardcoded secrets, weak crypto)
- **Logic review** — traces code paths for edge cases, null checks, boundary conditions, race conditions
- **Style compliance** — validates against project conventions (linting, formatting, naming, import organization)
- **Test adequacy** — flags untested code paths, missing edge cases, snapshot staleness
- **Performance hints** — spots N+1 queries, missing indexes, inefficient loops, memory leaks
- **Dependency risk** — flags vulnerable or unmaintained dependencies introduced

Each finding is posted as a PR comment with line references and suggested fixes. Review comments use GitHub's **suggested changes** format so maintainers can accept with one click.

## Git Blame Integration

Hermes uses git blame to understand code ownership:

- **Author-aware reviews** — knows who wrote each line, adjusts tone and detail level
- **Smart reviewer suggestion** — recommends reviewers based on file ownership and recent activity
- **Context preservation** — reads commit history to understand *why* code exists, not just *what* it does
- **Bus factor awareness** — flags changes to code only one person has touched

This prevents the awkward "I just reviewed my own PR" problem that naively automated systems create.

## CI Integration

Beyond PRs, Hermes hooks into CI pipelines:

- Analyzes test failures and suggests root causes (flaky test vs. real regression)
- Reviews deployment logs for anomalies (error spikes, latency regressions, error budget burn)
- Creates follow-up issues for flaky tests with reproduction steps
- Tracks code coverage trends across builds (flags drops >5%)
- **Cost attribution** — estimates compute cost per PR for budgeting

## Configuration: Making It Yours

Hermes's git workflow is configured in `.hermes/git-workflow.yaml`:

```yaml
# .hermes/git-workflow.yaml
git_workflow:
  branch_naming:
    pattern: "{type}/{scope}-{short-description}"
    types: [feat, fix, chore, refactor, docs, test, perf]
    max_length: 60

  commits:
    format: conventional
    sign: true                    # GPG/SSH signing
    co_authored_by: true          # Add co-author trailer
    max_files_per_commit: 10      # Split large changes

  pr:
    auto_create: true
    draft_by_default: false
    template: ".github/PULL_REQUEST_TEMPLATE.md"
    labels_from: [change_type, scope, size]
    reviewers_from: [git_blame, codeowners, recent_touch]
    required_approvals: 1
    auto_merge:
      enabled: true
      require_checks: true
      require_approvals: true
      method: squash              # merge, squash, rebase

  review:
    auto_review: true
    severity_threshold: warning   # error, warning, info
    categories:
      - security
      - logic
      - style
      - tests
      - performance
      - dependencies
    suggest_changes: true         # Use GitHub suggested changes format
    skip_generated: true          # Skip auto-generated files
    skip_vendored: true

  ci:
    watch_providers: [github_actions, gitlab_ci, circleci]
    analyze_failures: true
    create_followup_issues: true
    coverage_threshold: 5         # % drop triggers alert
```

## Real-World Workflows

### Dependency Updates (Fully Automated)

```bash
hermes schedule --cron "0 2 * * 1" --goal "update all npm dependencies, run tests, create PRs for each major version"
```

Hermes will:
1. Check for outdated packages weekly
2. Group updates by major/minor/patch
3. Run test suite for each group
4. Create separate PRs per package (or grouped for patch)
5. Auto-merge patch updates that pass; flag majors for review

### Refactoring Campaigns

```bash
hermes goal "refactor all async/await to use structured concurrency, one module per PR"
```

Hermes creates a **refactoring plan**, then executes it module by module — each as a separate PR with context-preserving commit messages linking back to the plan.

### Security Patch Backporting

```bash
hermes goal "backport the auth bypass fix from main to release/v2.1, release/v2.0"
```

Hermes identifies the minimal fix commit, cherry-picks cleanly, runs the relevant test suites on each branch, and opens backport PRs.
