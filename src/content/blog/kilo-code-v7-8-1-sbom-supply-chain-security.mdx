Kilo Code v7.8.1 dropped September 25, and it's the quietest important release of the year.

No new features. No UI changes. Just **CycloneDX software bills of materials published alongside every single artifact** — CLI archives, npm packages, container images, VS Code extension, and JetBrains plugin — each bound to its SHA-256 and signed as a GitHub attestation.

**That means you can now verify, cryptographically, that the Kilo Code binary you downloaded is exactly what the maintainers built. No supply-chain injection. No compromised dependency slipping in. No guessing.**

If you've been waiting for open-source coding agents to catch up to enterprise-grade supply-chain hygiene — **this is the release.**

## What an SBOM Actually Gives You

A Software Bill of Materials (SBOM) is a machine-readable inventory of every component in a build — direct dependencies, transitive dependencies, versions, licenses, and hashes.

**CycloneDX** is the industry-standard format (backed by OWASP, adopted by NTIA, required by US federal contracts).

**GitHub attestations** are cryptographic signatures that GitHub itself produces during the build, tying the SBOM to the exact commit and workflow run that produced it.

Together: you get a tamper-evident receipt for every Kilo Code artifact.

```bash
# Verify the CLI archive you downloaded
gh attestation verify kilo-darwin-arm64.zip \
  --repo Kilo-Org/kilocode \
  --signer-workflow build.yml
```

If the hash doesn't match, the attestation fails. Period.

## Why This Matters for *You* (Not Just Security Teams)

### 1. Your Editor Extension Can't Be Silently Swapped

The VS Code Marketplace and JetBrains Marketplace are generally trustworthy — but they're centralized. If a maintainer's account is compromised, or a marketplace is breached, a malicious update could push to thousands of developers.

With SBOM attestations: **you (or your IT team) can pin the exact artifact hash and verify it before install.** No trust required.

### 2. Container Images Are Now Auditable

```dockerfile
# Before: you pulled kilocode/kilo:latest and hoped
# After: you verify the SBOM attestation for that exact digest
docker pull kilocode/kilo@sha256:abc123...
gh attestation verify kilocode/kilo@sha256:abc123... --repo Kilo-Org/kilocode
```

CI pipelines can now gate deployments on attestation verification. **Supply-chain security becomes a CI check, not a prayer.**

### 3. Compliance Just Got Easier

If your org requires SBOMs for vendor software (EO 14028, EU CRA, FedRAMP, SOC 2) — **Kilo Code now ships them automatically.** No vendor questionnaire. No manual requests. The artifacts *are* the evidence.

### 4. Dependency Drift Is Now Visible

The SBOM lists every transitive dependency with its version and hash. If a future release unexpectedly pulls in a new dependency (or a compromised version of an existing one), **the SBOM diff shows it immediately.**

Security teams can diff SBOMs between releases instead of reading changelogs and hoping.

## The Patch That Enabled It

The change is surprisingly small: **PR #14513** adds CycloneDX generation to the release pipeline and uploads each SBOM as a GitHub attestation.

```yaml
# Simplified from .github/workflows/release.yml
- name: Generate CycloneDX SBOM
  uses: CycloneDX/cyclonedx-github-action@v1
  with:
    output: sbom.json
- name: Attest SBOM
  uses: actions/attest-build-provenance@v2
  with:
    subject-path: dist/kilo-linux-x64.tar.gz
    subject-name: kilo-linux-x64.tar.gz
    predicate-path: sbom.json
    predicate-type: https://cyclonedx.org/schema/bom-1.6
```

That's it. The rest is GitHub's infrastructure doing the heavy lifting.
