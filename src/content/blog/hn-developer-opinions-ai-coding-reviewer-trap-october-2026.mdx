Last week, a 40-year veteran developer posted on Hacker News: *"I didn't see the end coming. AI writes most of the code now. I've turned into a full-time reviewer. Worst of all, I no longer enjoy the satisfaction of solving hard problems on my own anymore."*

The thread exploded with 15+ comments from developers across experience levels — from 1990s sysadmins to founders running AI-first companies. Meanwhile, another thread detailed a 60-hour Claude Code project that started fast and ended in a "bug treadmill" where the AI broke as much as it fixed.

These aren't marketing narratives. They're developers talking to developers when no PR team is watching.

## What Happened: Two Threads, Same Underlying Anxiety

**Thread 1: "40 years of writing code. I didn't see the end coming"** (18 points, 15 comments)

A developer who started when code shipped on floppy disks described the shift: AI handles generation, humans handle review. The creative satisfaction — the "aha" moment of cracking a hard problem — is gone. The question: *Has AI given you back your time, or taken something you loved?*

**Thread 2: "The failure modes of Claude Code in a guided 60h project"** (2 points, 1 comment linking to a 11,000-word post-mortem)

An engineer guided Claude Code to build a semantic fuzzer for Obsidian Sync. First 30 hours: functional prototype, ~10 hours saved. Next 30 hours: bug treadmill. Each fix introduced new regressions. The author concluded: *"The only growth was my dependency on it. A junior would have grown."*

## The Real Insight: Reviewing Is Not the Same as Writing

The hmijail post-mortem is the most technically detailed account I've seen of long-horizon AI coding. Key findings:

**Context rot is real.** After ~30 hours, Claude's context window filled with stale assumptions. The author had to manually rewind conversations — something Anthropic's own docs recommend but don't automate.

**Thinking ≠ doing.** Claude would reason correctly in its chain-of-thought, then generate code contradicting that reasoning. The "I supervise the thinking but not the code" model fails when the model lies to itself.

**Subagents failed.** Isolated subagents lost critical context from the main conversation, returning confidently wrong summaries. The author abandoned them.

**No institutional memory.** Every new session re-derives context. A human builds mental models; the AI rebuilds them from scratch each time.

**The "AI psychosis" trap.** Extended conversations with sycophantic models create shared delusions. The author caught himself accepting confident hallucinations because they *sounded* right in context.

## What This Means for You

### If you're a beginner

Don't skip the struggle. The developers mourning lost craft *earned* that craft through thousands of hours of debugging, reading source, and hitting walls. AI can give you answers, but it can't give you the intuition that comes from earning them.

**Practical rule:** Write the first implementation yourself. Use AI for refactoring, tests, and boilerplate *after* you understand the problem.

### If you're a senior IC

You're not a reviewer. You're an architect. The trap is treating AI output as a PR to approve. Instead:

- **Constrain context ruthlessly.** Short sessions, fresh starts, explicit handoffs.
- **Verify at boundaries.** Don't review line-by-review; test contracts and invariants.
- **Keep a human in the loop for architecture.** AI optimizes locally; you optimize globally.

### If you're a founder / solo builder

The leverage is real. But hmijail's 60-hour project shows the cliff: velocity drops sharply once context rots. Build tooling that:

- Forces session boundaries (like the Ralph Wiggum loop)
- Persists architectural decisions outside the conversation
- Makes context visible and manageable

### If you manage a team

**"Vibe coding" doesn't scale.** The hmijail experiment was one expert supervising one AI. Add a team, and you get:

- Inconsistent context across developers
- No shared mental model of what the AI "knows"
- Review bottlenecks on AI-generated code nobody truly owns

Invest in **harnesses, not prompts.** The Grist harness (Show HN, 0 comments but technically interesting) routes easy tasks to cheap models, hard tasks to frontier models, injects team standards via "doctrine injection," and adds verification hooks. That's the shape of production AI workflows.

## The Uncomfortable Question Nobody Answers

hmijail ends with a challenge: *If you believe any LLM is good enough by itself, build a similar fuzzer from scratch, let it cook, show it finds bugs, then explain what you did differently.*

No one has taken that challenge publicly.

The HN threads reveal a quiet consensus: **AI coding agents are power tools, not autopilots.** They amplify skill but don't replace the need for it. The developers who thrive aren't the ones prompting hardest — they're the ones who never stopped building their own mental models.
