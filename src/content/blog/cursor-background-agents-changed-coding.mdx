Cursor's background agents are the most underrated feature in AI coding right now.

While everyone debates Claude Code vs Cursor for interactive coding, Cursor quietly shipped something that changes the workflow entirely: agents that work while you don't.

## Foreground versus background

Start a task, switch to something else, come back to finished code. Not a suggestion — actual completed work. File changes, tests passing, ready to review.

The psychology shift is significant. When an agent works in the foreground, you watch it. You intervene. You micromanage. When it works in the background, you trust it. You focus on architecture, design, the hard problems. The agent handles the implementation details.

This is how coding should work. Humans do the thinking. Agents do the doing. Cursor's background agents are the first to make this feel natural in an IDE.

The Composer feature extends this. Multi-file edits that span your entire codebase, not just the file you're looking at. Describe what you want, and Cursor handles the coordination across files, imports, types, and dependencies.

## A typical background-agent session

Here's what a real session looks like now:

```bash
# 09:00 - Kick off a refactor while coffee brews
cursor-agent "Extract the authentication middleware into its own package, 
  add TypeScript interfaces, and update all imports across the monorepo"

# 09:05 - Switch to design review, architecture discussion
# 09:30 - Come back: 12 files changed, tests passing, ready to review
git diff --stat
#  12 files changed, 847 insertions(+), 234 deletions(-)
```

The agent handles the mechanical work: finding all import sites, updating type signatures, running the test suite, fixing the inevitable type errors. You review the diff, approve the PR, move on.

## What makes it different from async CLI tools

Codex CLI runs in the cloud with worktrees. It's powerful but disconnected from your editor — you get a PR at the end, not an interactive diff in your workspace. GitHub Copilot Workspace is similar: cloud-first, review-later.

Cursor's background agents run **inside your IDE**. They have your full context: the open files, your git history, your test runner, your LSP. When they finish, the changes are already in your working tree. You don't context-switch to a browser to review.

## The trust calibration curve

The first week, you babysit. You check every file. By week three, you're kicking off three agents before lunch and reviewing the batch over coffee. The calibration is explicit:

| Week | Behavior | Review time |
|------|----------|-------------|
| 1 | Watch every step, intervene constantly | 80% of task time |
| 2 | Check diffs before apply, run tests manually | 40% of task time |
| 3+ | Batch review, trust the test gate | 10% of task time |

The test gate is the key. Background agents run your test suite before presenting work. If tests pass, the mechanical correctness is verified. Your review becomes architectural: does this solve the right problem? Is the abstraction clean?

## Where it lands in the market

The $20/month subscription is a bargain for what you get. Background agents alone would be worth it. Combined with Composer, inline editing, and the fast model switching, Cursor is the most complete coding environment available.

The limitation is terminal integration. Cursor is an IDE — it lives in its own window. For developers who live in the terminal, this is a friction point. But for everyone else, Cursor is the daily driver.

The background-agent pattern is now the front line of the category. ## What's still missing

- **No persistent agent memory across sessions** — each task starts fresh
- **No cross-repo coordination** — monorepo support is good, multi-repo is manual
- **No cost visibility** — you don't see token burn per agent task (unlike [Claude Code's hidden utilization](/blog/claude-code-rate-limit-utilization/))

These are solvable. The pattern is proven.
