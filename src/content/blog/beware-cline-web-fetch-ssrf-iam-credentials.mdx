**TL;DR:** Cline's built-in `web-fetch` tool fetches **any** `http(s)` URL with **no host or address guard** and follows redirects by default. A prompt-injected webpage — or a model that's been steered by malicious content — can make it read `http://127.0.0.1:<port>/...`, other loopback and link-local addresses, and on a cloud VM/container the **`169.254.169.254` metadata endpoint**, returning IAM credentials straight into the model context. The issue ([cline/cline #13494](https://github.com/cline/cline/issues/13494), filed Aug 23, 2026) is **still open, with no fix merged** as of September 11, 2026.

This is a Server-Side Request Forgery (**SSRF** — read flavor) in the trust boundary every AI coding agent depends on: the tool that fetches URLs on your behalf.

---

## What Happened

On August 23, 2026, a researcher filed [cline/cline issue #13494](https://github.com/cline/cline/issues/13494): "security: `web-fetch` tool fetches loopback/link-local/cloud-metadata URLs unchecked - SSRF of local services & IAM creds into the model context."

The report is **code-verified against Cline's HEAD at the time** (and my own check of the file at HEAD on September 11, 2026 confirms nothing has changed). The vulnerable code is `sdk/packages/core/src/extensions/tools/executors/web-fetch.ts`:

- **`followRedirects = true` by default** (line 106) — requests are built with `redirect: "follow"` (line 151), so a public URL that responds with a `302` gets followed **cross-host**, including to loopback and metadata endpoints.
- **The only scheme check is http/https** — there is no hostname/IP validation. The file contains **zero** references to `127.`, `169.254`, `localhost`, loopback, private IP, or link-local.
- A "manual" redirect mode exists but is **off by default**, and even when enabled it would only refuse a `3xx` — a **direct** loopback or metadata URL would still be fetched happily.

**Consequence:** `web-fetch` reaches anything on the machine. No custom credentials are attached to the request, so the impact is SSRF-read / confidentiality (the reporter estimates ~CVSS 5.3–5.9). But that's not a comfort — read-SSRF to the metadata endpoint gives an attacker **your cloud IAM credentials**, and this agent runs in your trusted context where the model is *supposed* to act on what it reads.

## Who Is Affected

**You are affected if you use Cline** (VS Code extension or CLI) **and the `web-fetch` tool exists in your toolchain** — it's a built-in executor that ships with the product, so for most users it's simply available. The trigger is a URL the model decides to fetch, which means:

- **Anyone running Cline on a cloud VM, container, or Kubernetes pod** — the metadata endpoint `http://169.254.169.254/latest/meta-data/iam/security-credentials/<role>` returns IAM role credentials that let whoever holds them **act as the machine's cloud role** (AWS, GCP, Azure, Alibaba all expose IMDS-style endpoints; that IP range is the universal one).
- **Anyone with local services on localhost** — databases, dev servers, admin panels, internal APIs, Docker sockets — the tool will read them and put the content in the conversation.
- **Any Cline session that has ever processed untrusted content** — even a single fetched webpage, an MCP tool result, a README, or a code snippet that a malicious actor controls can steer the model toward a URL it shouldn't fetch.

This isn't a hypothetical "attacker on your box" scenario. The realistic chain is:

1. You ask Cline to research a webpage, or it reads a repo file / MCP resource containing attacker-controlled text.
2. That content contains a crafted URL (direct `http://169.254.169.254/...` or a public URL that redirects there).
3. The model calls `web-fetch` on it — it works, returns the IAM JSON into the conversation.
4. The model is now operating with your cloud credentials visible in context and can be steered to use them.

The same class of bug was independently reported against **Opencode** ([anomalyco/opencode #36376](https://github.com/anomalyco/opencode/issues/36376), July 11, 2026 — still open) and a fix **proposed but not merged** for Goose ([aaif-goose/goose PR #11501](https://github.com/aaif-goose/goose/pull/11501), Aug 23, 2026). This is a broad pattern in the 2026 coding-agent wave: agents fetch on your behalf, and the URL → trust boundary is being built from scratch everywhere.

## How to Check If You're Affected

The cleanest check is to reproduce it locally (safe, no cloud needed):

```bash
# 1. Spin up a local secret on a loopback port
python3 -m http.server 9191 --directory /tmp/cline-probe &
echo "super-secret-local-value-12345" > /tmp/cline-probe/secret.txt

# 2. In any Cline session, ask:
#    "fetch http://127.0.0.1:9191/secret.txt and tell me what's in it"
# 3. If the value appears in the conversation → your web-fetch is unguarded.
```

If you're on a cloud VM, you can check without even calling Cline whether the metadata endpoint is reachable from your environment (`curl -s http://169.254.169.254/latest/meta-data/` — on AWS this should return something; on bare-metal it will hang or refuse). If that endpoint is reachable and Cline's `web-fetch` is unguarded, the exposure is real. *(I did not run the probe against a live Cline instance for this writeup — the report's POC, `trickyfalcon/cve-hunt/poc-cline/webfetch_ssrf.mjs`, demonstrates the exact construction, and the source inspection is conclusive: there is no guard in the file.)*

## Is There a Fix?

**No merged fix as of September 11, 2026.** The issue is open, tracked internally as CLINE-3049. The reporter's proposed fix (the same pattern already applied to Goose's guard) is to keep following redirects — because legitimate CDNs and servers redirect — but **reject client-local targets before connecting**:

```ts
const PRIVATE_HOST = /^(0\.|10\.|127\.|169\.254\.|172\.(1[6-9]|2\d|3[01])\.|192\.168\.)/;
function isPrivateHostname(host: string): boolean {
  const h = host.trim().toLowerCase().replace(/\.$/, "");
  if (h === "localhost" || h.endsWith(".localhost")) return true;
  if (h === "::" || h === "::1" || h.startsWith("fe80:")) return true; // IPv6 loopback / link-local
  return PRIVATE_HOST.test(h);
}
```

The key hardening details: **check the final request URL after redirects**, and unconditionally deny loopback + link-local (`169.254/16`, IPv6 equivalents). Whether to also deny RFC1918 (`10/8`, `172.16/12`, `192.168/16`) is a tradeoff — the Goose guard intentionally leaves RFC1918 allowed so legitimate internal-hosted URLs keep working, but many teams will want the stricter toggle.

## How to Protect Yourself Until It's Patched

There's no Cline-side config to deny loopback fetches today, so defense is layered:

1. **Review your Cline permission rules** — do not grant blanket `always: ["*"]` permission on the fetch/browser tools. If you can scope the tool or deny it, do. (Opencode's report explicitly flags that `always: ["*"]` webfetch rules make this worse; the same logic applies in Cline.)
2. **Treat model context as untrusted input** — anything the agent fetched, or any MCP/resource content, can steer it to a malicious URL. Don't let the agent run with elevated credentials while processing unknown content.
3. **Harden the metadata endpoint** — if you run Cline in cloud VMs/containers, use **IMDSv2 with a hop-limit of 1** (AWS `PutInstanceMetadataOptions` / `MetadataOptions HttpTokens=required HttpPutResponseHopLimit=1`). That doesn't stop the read from a local process, but it raises the bar. Apply equivalent protections on GCP/Azure if available.
4. **Run agent work in a disposable sandbox** (Docker container without host networking, no cloud role attached, minimal localhost surface). This is the single most effective mitigation: if the fetch can only reach an empty container, read-SSRF has nothing to steal.
5. **Watch the issue** ([#13494](https://github.com/cline/cline/issues/13494)) and upgrade the moment a fix lands. The first Cline release that hardens `web-fetch.ts` is the one to adopt.

## Bottom Line

This is a quiet, unpatched, code-verified SSRF hole in a mainstream coding agent's built-in fetch tool. It won't crash anything, it won't pop a terminal — and that's exactly why it's dangerous. The blast radius is your localhost surface and, on cloud VMs, your IAM credentials, delivered to the model context where a hostile page can then steer them. If you run Cline on cloud infrastructure or with access to sensitive local services, treat this as a reason to scope that tool down today, not next week.
