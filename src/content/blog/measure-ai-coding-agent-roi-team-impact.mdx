Your team has been using AI coding agents for three months. The vibes are good — developers *feel* faster. But your CTO just asked: **"What's the ROI?"**

You could say "developers are happier" or "we ship faster." That works until the budget review. Then you need numbers.

This article gives you a measurement framework that:
- **Takes 15 minutes/week to maintain** (not hours of manual logging)
- **Uses data you already have** (Git, CI, ticketing, API bills)
- **Produces a one-page dashboard** leadership can actually read
- **Catches the traps** that make AI look better/worse than it is

---

## The Trap: What Most Teams Measure (And Why It's Wrong)

| What Teams Track | Why It Misleads |
|------------------|-----------------|
| Lines of code generated | AI writes verbose code. More LOC ≠ more value. |
| PRs merged per week | Could mean smaller PRs, not more output. |
| "Time saved" estimates | Humans are terrible at estimating counterfactuals. |
| Token spend | Cost without context. $500/month could be a bargain or a waste. |

**The only metric that matters: Did the team deliver more *verified, working* value per dollar spent?**

## The Framework: Four Metrics, One Dashboard

### 1. Verified Throughput (The Output Metric)
**Definition:** `Tickets/week that reach "Done" with passing tests and human review`

Not "PRs opened." Not "commits pushed." **Verified done.**

```bash
# Pull from your ticketing system (Linear, Jira, GitHub Projects)
# Filter: status = Done, resolved in sprint, has test coverage > 80%
# Group by: week, assignee, agent-used (yes/no)
```

**Why it works:** Filters out AI-generated code that breaks in staging. Measures what actually ships.

### 2. Cycle Time Delta (The Speed Metric)
**Definition:** `Median cycle time (ticket created → verified done) with agent vs without`

```bash
# From your Git + ticketing data
# Ticket created at: Linear/Jira timestamp
# Verified done at: PR merged + CI green + reviewer approval timestamp
# Compare: agent-assisted tickets vs non-agent tickets (same repo, same complexity tier)
```

**Why it works:** Controls for ticket size. A 50% cycle time reduction on medium tickets is a real signal.

### 3. Rework Rate (The Quality Metric)
**Definition:** `% of agent-assisted PRs that need follow-up fixes within 2 weeks`

```bash
# Track: PRs where agent was used (label: "ai-assisted")
# Measure: Hotfixes/reverts within 14 days of merge
# Compare: Rework rate (agent) vs Rework rate (human-only)
```

**Why it works:** Catches the "AI moves fast but breaks things" pattern. If rework rate doubles, speed gains evaporate.

### 4. Cost per Verified Ticket (The Money Metric)
**Definition:** `(Agent subscription + API tokens + human review time) / Verified tickets delivered`

```python
# Monthly calculation
agent_cost = subscription_cost + api_token_cost
review_hours = sum(pr_review_minutes for ai_prs) / 60
review_cost = review_hours * avg_eng_hourly_rate
total_cost = agent_cost + review_cost

cost_per_ticket = total_cost / verified_tickets_delivered
```

**Why it works:** Includes the hidden cost of *reviewing* AI output. If agents generate 3x PRs but each takes 2x review time, the math changes.

## The 90-Day Protocol (What to Do Each Month)

### Month 1: Baseline (Weeks 1-4)
**No agents.** Measure the four metrics on pure human output. This is your control group.
- Get 4 weeks of clean baseline data
- Document: team size, repo complexity, typical ticket types

### Month 2: Rollout (Weeks 5-8)
**Gradual adoption.** 25% of tickets agent-assisted → 50% → 75%.
- Label every agent-assisted PR
- Track which *types* of tickets benefit (bug fixes? features? refactors? tests?)
- Watch rework rate closely — this is where early adoption fails

### Month 3: Optimization (Weeks 9-12)
**Double down on what works. Kill what doesn't.**
- If bug fixes improve but features don't → restrict agent to bug fixes
- If rework rate spikes on complex tickets → add mandatory human design review before agent starts
- If cost/ticket plateaus → negotiate volume discounts, switch models, add caching

## The Traps That Invalidate Your Data

### Trap 1: Ticket Size Creep
**Symptom:** Cycle time drops but tickets get smaller.
**Fix:** Normalize by story points or ticket complexity tier (S/M/L/XL). Compare S vs S, M vs M.

### Trap 2: Review Theater
**Symptom:** Review hours drop because reviewers rubber-stamp AI PRs.
**Fix:** Track *review depth* — comments per PR, files reviewed, time spent. Shallow reviews = hidden rework later.

### Trap 3: Selection Bias
**Symptom:** Team only uses agents on easy tickets.
**Fix:** Randomize. Assign 50% of similar tickets to agent, 50% to human. Blind the reviewer.

### Trap 4: Model Drift
**Symptom:** Metrics improve, then silently degrade when provider switches models.
**Fix:** Pin model versions in your agent config. Track which model version produced each PR.

## What Good Looks Like (Benchmarks from 2026 Data)

| Metric | Baseline (Human) | Healthy Agent Adoption | Warning Signs |
|--------|------------------|------------------------|---------------|
| Verified tickets/engineer/week | 3-4 | 4-6 (+25-50%) | < 3 or > 8 (quality risk) |
| Cycle time (M ticket) | 4-5 days | 2.5-3.5 days | No change or increase |
| Rework rate | 8-12% | 8-12% (same) | > 15% |
| Cost per verified ticket | $400-600 | $300-450 | > $600 |
| Agent-assisted % | 0% | 40-60% | > 80% (over-reliance) |

**The sweet spot:** 40-60% agent-assisted tickets, same rework rate, 30% cycle time improvement, 25% cost reduction.
