AmpCode **November 5** dropped **GitLab Integration** — your agent can now connect to GitLab.com and your self-managed GitLab instances. Create merge requests, review code, resolve vulnerabilities, all from inside your Amp thread.

---

## The One-Line Summary

**Your Amp agent just became a GitLab power user. Point it at a GitLab repo — it creates MRs, reviews code, fixes vulnerabilities, and ships. Works on GitLab.com and your self-hosted instance.**

---

## What the GitLab Integration Actually Does

Each person connects GitLab in **Settings → Integrations & MCP → GitLab**. Once connected:

1. **Your agent sees your GitLab projects** — no manual repo cloning
2. **Creates merge requests** — writes code, opens MR, describes changes
3. **Reviews merge requests** — reads diffs, leaves comments, suggests fixes
4. **Resolves vulnerabilities** — GitLab SAST/DAST findings become agent tasks
5. **Works on self-hosted GitLab** — not just GitLab.com; your on-prem instance works too

---

## Why This Matters for Teams on GitLab

### Before: Context Switching Hell
- See vulnerability in GitLab → copy details → switch to Amp → explain context → agent fixes → copy back → create MR → wait for review

### After: Agent Lives in GitLab
- GitLab SAST flags SQL injection → **agent picks it up automatically** → reads code → writes fix → opens MR with description → you review → merge

```markdown
# Real workflow from Amp's team

Thread: "Fix GitLab SAST finding GL-SAST-1234"
1. Agent: "I see the finding in project `team/payments`. Reading the vulnerable file..."
2. Agent: *opens `src/auth/token.rs`, finds the unsanitized input*
3. Agent: "Creating fix and opening MR..."
4. → MR #847 created: "Fix SQL injection in token validation"
5. You: *review diff, click Approve*
6. Agent: "Merged. Vulnerability resolved in GitLab."
```

## Self-Hosted GitLab: Your Instance, Your Agent

This isn't GitLab.com only. **Self-managed GitLab works the same way:**

- Connect your `gitlab.company.com` instance
- Agent uses your existing OAuth/tokens
- MRs, reviews, CI pipelines — all internal
- No data leaves your network (orbs run in your infra if you use self-hosted orbs)

```bash
# Setup (one-time per workspace member)
# 1. In Amp: Settings → Integrations & MCP → GitLab
# 2. Enter your GitLab URL (https://gitlab.company.com)
# 3. Authorize with OAuth or Personal Access Token
# 4. Select projects the agent can access

# Now in any thread:
amp thread create "Review MR #1234 in team/backend"
amp thread create "Fix all Critical SAST findings in team/api"
amp thread create "Create MR for JIRA ticket PAY-567"
```

## Quick Start: Your First GitLab-Powered Thread

```bash
# 1. Connect GitLab (one-time)
# Settings → Integrations & MCP → GitLab → Connect

# 2. Create a vulnerability-fixer thread
amp thread create --service-account team-amp \
  "Monitor GitLab SAST in team/payments, auto-fix Critical/High findings"

# 3. Create a code-review thread
amp thread create --service-account team-amp \
  "Review all open MRs in team/backend with label 'needs-review'"

# 4. Create a feature-thread
amp thread create "Implement JIRA PAY-567: idempotency keys for /payments"
# → Agent reads JIRA (if connected), writes code, opens MR on GitLab
```

## What's Still Missing (Honest Assessment)

- **GitLab CI/CD variables** — agent can't read masked/protected variables yet (security)
- **Group-level MR policies** — agent respects but can't configure approval rules
- **Multi-repo MRs** — single MR per repo; no cross-repo atomic changes yet
- **GitLab Pages preview** — no automatic preview deployment from agent MRs (coming)
