Every CLI tool has this problem at some point: the parser eats an argument that was meant for something else. Gitlawb Zero just fixed one of the most annoying instances of this.

## The Bug

When you ran Zero with a flag that takes a value, the parser would sometimes consume the next positional argument as the flag's value.

Example:
```
zero --model gpt-4 myfile.txt
```

Before the fix, `myfile.txt` might get consumed as part of `--model`'s value instead of being treated as a positional argument. The result: the file never gets processed, and you get a confusing error about the model not existing.

## The Fix

`fix(cli): prevent consuming positional arguments as flag values (#619)`

The fix adds proper boundary detection between flag values and positional arguments. The parser now correctly distinguishes between:
- `--flag value` (flag with value)
- `--flag value positional` (flag with value + positional)
- `value positional` (two positionals)

The implementation uses a lookahead strategy: when a flag expecting a value encounters the next token, it checks whether that token looks like another flag (starts with `-`) or is a bare word. Bare words after a flag value are preserved as positionals.

## Why This Matters

CLI parsing bugs are frustrating because they break the most basic workflows. You type a command exactly as documented, and it does something unexpected. The fix is invisible — commands now do what you typed. But that's exactly the point: good infrastructure is invisible.

Zero has over 40 CLI flags across subcommands (`zero run`, `zero config`, `zero session`, `zero mcp`, etc.). Each flag that accepts a value was a potential failure point. Users scripting Zero in CI/CD pipelines, git hooks, or shell aliases were hitting this silently — commands would appear to succeed but process the wrong files.

The bug was particularly insidious because it only triggered when a flag value was followed by a bare-word positional argument. Flags followed by another flag (e.g., `--model gpt-4 --temp 0.7`) worked fine. But `--model gpt-4 myfile.txt` would consume `myfile.txt` as the model value. This pattern appears constantly in real workflows: specifying a model, then a file to operate on.

## Root Cause and Technical Detail

The regression was introduced in v0.4.0 when the CLI parser was refactored to support subcommand-specific flag sets. The original parser used a simple state machine: when it saw a flag that takes a value, it consumed the next token unconditionally. The refactor added subcommand context but kept the same greedy consumption logic.

PR #619 rewrites the flag-value boundary detection. The new logic:

1. When a flag expecting a value encounters the next token, it peeks at the token
2. If the token starts with `-`, it's another flag — stop, don't consume (flag value is empty or missing)
3. If the token is a bare word, consume it as the flag value
4. The **critical addition**: after consuming a flag value, if the *next* token is also a bare word, preserve it as a positional — don't let the flag consume multiple positionals

This lookahead strategy is the same approach used by mature parsers like `argparse` (Python) and `Commander.js` (Node), but implemented in Zero's custom Rust-based CLI layer for zero-dependency binary distribution.

## What This Means

Zero's CLI is now more reliable. Flag-heavy commands (which Zero has many of) work as expected. For users scripting Zero or integrating it into workflows, this eliminates a class of silent bugs.

### CI/CD Pipeline Impact

The fix is especially valuable for automated workflows. A typical CI step might look like:

```yaml
- name: Run Zero agent
  run: zero run --model gpt-4 --max-turns 10 --session ci-run ./src
```

Before the fix, `./src` could be consumed as part of `--max-turns` if the parser was in a bad state, causing the agent to run in the wrong directory with no error — just silently wrong results. Now the boundary is explicit: `--max-turns 10` consumes `10`, then `./src` is correctly identified as the positional working directory argument.

### Common Patterns That Now Work

```bash
# Multiple flags with values followed by positionals
zero --model gpt-4 --temperature 0.7 --max-tokens 4000 src/index.ts

# Config flags mixed with files
zero config --provider anthropic --model claude-3-opus my-config.json

# Session management with file args
zero session --name "feature-branch" --resume ./project-root
```

## The Broader Pattern: CLI Reliability in AI Agents

This bug highlights a recurring theme in coding agents: **CLI reliability is table stakes for adoption**. An agent that works beautifully in a chat interface but breaks when scripted won't survive in production workflows. Zero's architecture — a native binary with a TUI — means the CLI *is* the primary interface for many users. Fixing flag parsing isn't a feature; it's respect for the operator's time.
