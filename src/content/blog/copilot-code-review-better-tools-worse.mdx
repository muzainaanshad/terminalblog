GitHub's engineering team just published a confession that should make every coding-agent builder sit up: when they upgraded Copilot's code-review agent with richer, more Unix-style tools for exploring a repo, review quality went *down*, not up. Then they fixed it — and the fix is the interesting part.

The instinct is obvious. An agent that can run `grep`, `git log`, read files, trace call paths — that's a more capable reviewer, right? More context, better comments. But capability isn't the bottleneck. Attention is. When you hand an agent a wider toolbox, it doesn't spend that budget on deeper reasoning about your change. It spends it *exploring*. The model burns its inference budget flailing across the codebase instead of forming a judgment about the diff in front of it. Better tools, worse review.

What actually moved the needle wasn't more exploration. It was anchoring the agent to *evidence* — reshaping the workflow so review is organized around the pull request itself: the diff, the description, the linked context. The tools stopped being a open playground and became a targeted retrieval layer that the agent consults on demand, not a default mode.

This should reframe how we think about "agentic" features. The race is not to stuff agents with the largest toolset. It's to design the loop so the model's limited reasoning budget is spent on the decision, not the navigation. A smaller, better-bounded tool surface that keeps the agent tethered to the task will beat a sprawling one every time.

We see the same pattern elsewhere in the ecosystem this week: agents adding usage limits, retry handling, and session rewrites — all attempts to keep the model pointed at the job instead of spiraling. The Copilot lesson is a clean statement of the principle. If your agent feels dumber after you "improved" it, look at whether you gave it more ways to get distracted, not more ways to think.

For anyone building or evaluating coding agents: stop counting tools. Start measuring whether the agent actually spends its attention on your problem. That's the only capability metric that correlates with output quality.
