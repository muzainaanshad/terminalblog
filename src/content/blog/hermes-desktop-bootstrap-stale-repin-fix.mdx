## Implementation Deep Dive: Release Manifest Validation

The core of the fix is the release manifest — a JSON file published with each Hermes Desktop release that lists all valid commits for that release:

```json
{
  "version": "0.21.6",
  "latestCommit": "def456",
  "commits": ["abc123"
  - "def456"
  - "ghi789"
  - "jkl012",
  "configSchemaVersion": 3,
  "migrations": {
    "abc123": ["rename: oldFlag → newFlag"
  - "deprecate: legacyMode",
    "ghi789": ["add: newFeatureFlag"
  }
}
```

The bootstrap fetches this manifest from the GitHub releases API and validates the existing checkout against it:

```typescript
interface ReleaseManifest {
  version: string;
  latestCommit: string;
  commits: string[];
  configSchemaVersion: number;
  migrations: Record<string, Migration[]>;
}

async function validateCheckout(checkout: Checkout): Promise<ValidationResult> {
  const manifest = await fetchReleaseManifest();
  
  // Direct validation: is the current commit in the manifest's valid list?
  const isValid = manifest.commits.includes(checkout.currentCommit);
  
  // Staleness check: is the current commit behind the latest?
  const isStale = !isValid && manifest.latestCommit !== checkout.currentCommit;
  
  // Corruption check: does the checkout directory have all expected files?
  const isCorrupted = await verifyCheckoutIntegrity(checkout.path);
  
  return { isValid, isStale, isCorrupted, manifest };
}
```

This approach is superior to simple version comparison because:
1. **Release manifests can include multiple valid commits** (e.g., hotfix branches, backported fixes)
2. **Config schema versions are tracked per-release** — migrations know exactly what schema they're migrating from and to
3. **Rollback-safe** — if a release is pulled, the manifest for the previous release remains valid

## Config Migration Engine: Under the Hood

The migration engine is the unsung hero that makes repins painless. When a repin *is* needed, it doesn't just swap commits — it transforms your config:

```typescript
interface Migration {
  type: 'rename' | 'deprecate' | 'add' | 'remove' | 'transform';
  fromKey?: string;
  toKey?: string;
  defaultValue?: unknown;
  transform?: (value: unknown) => unknown;
}

async function migrateConfig(
  fromCommit: string, 
  toCommit: string, 
  manifest: ReleaseManifest
): Promise<ConfigMigrationResult> {
  const migrations = computeMigrations(fromCommit, toCommit, manifest);
  const results: MigrationResult[] = [];
  
  for (const migration of migrations) {
    switch (migration.type) {
      case 'rename':
        if (config[migration.fromKey!] !== undefined) {
          config[migration.toKey!] = config[migration.fromKey!];
          delete config[migration.fromKey!];
          results.push({ type: 'rename', from: migration.fromKey, to: migration.toKey });
        }
        break;
      case 'deprecate':
        if (config[migration.fromKey!] !== undefined) {
          logger.warn(`Config option ${migration.fromKey} is deprecated and will be removed`);
          results.push({ type: 'deprecate', key: migration.fromKey });
        }
        break;
      case 'add':
        if (config[migration.toKey!] === undefined && migration.defaultValue !== undefined) {
          config[migration.toKey!] = migration.defaultValue;
          results.push({ type: 'add', key: migration.toKey, value: migration.defaultValue });
        }
        break;
      case 'transform':
        if (config[migration.fromKey!] !== undefined && migration.transform) {
          config[migration.fromKey!] = migration.transform(config[migration.fromKey!]);
          results.push({ type: 'transform', key: migration.fromKey });
        }
        break;
    }
  }
  
  await saveConfig(config);
  return { applied: results };
}
```

Desktop apps for AI agents are relatively new. The update process is one of the trickiest parts — you need to handle:

- Existing installations that work
- Fresh installations that need full setup

Hermes Desktop's bootstrap repin fix shows attention to the existing user experience. It's not enough to make new installations work — you need to make existing installations survive updates.

## FAQ

**Q: Does this affect fresh installs?**
No. Fresh installs always get the latest commit. The fix only changes behavior for *existing* checkouts.

**Q: What if I *want* to force a repin?**
Use `hermes-desktop update --force-repin` to skip the validity check and repin to latest.

**Q: How do I know if my config was migrated?**
Check the Hermes Desktop logs: `~/Library/Logs/Hermes Desktop/` (macOS) or `%APPDATA%\Hermes Desktop\logs\` (Windows). Look for "Migrated config:" entries.

**Q: Can this cause issues with downgrades?**
Downgrades are explicitly handled: if you install an older release, the validity check fails (new commit not in old manifest), triggering a proper repin and config migration to the older schema.
