The best fixes are the ones you didn't know you needed until you see them. Oh My Pi's latest commit fixes a subtle but painful bug in mnemonic extraction: empty structured results were being silently dropped.

The fix: `fix(mnemopi): preserve empty structured extraction`.

## The Bug: Silent Data Corruption

Oh My Pi uses mnemonic structured extraction to parse data from agent outputs into structured formats — JSON, tables, schemas. When a field was legitimately empty, the extraction pipeline would skip it entirely instead of preserving it as an empty value.

This meant:
- An empty array became `undefined` instead of `[]`
- A null field disappeared instead of being `null`
- An empty string became missing instead of `""`

For workflows that validate output schemas, this was a **silent data corruption**. Your agent thought it was extracting correctly, but the data was subtly wrong.

### Why This Happened

The extraction pipeline used a "truthy" check to filter results:

```typescript
// Before (buggy)
const extracted = Object.fromEntries(
  Object.entries(raw).filter(([, v]) => v)  // drops falsy: [], "", null, 0, false
);
```

This looks reasonable until you realize that in structured extraction, **empty is meaningful data**. An empty array of test failures means "no failures found" — not "field missing." A null `error` field means "no error" — not "error field doesn't exist."

## The Fix

```typescript
// After (fixed)
const extracted = Object.fromEntries(
  Object.entries(raw).filter(([, v]) => v !== undefined)  // preserves [], "", null, 0, false
);
```

The change is minimal — one character (`!== undefined` vs truthy) — but the impact is massive for correctness.

## Why This Matters for Coding Agents

Structured extraction is the backbone of agent-to-tool communication. When an agent:
- Extracts data from a web page
- Parses an API response
- Converts natural language to structured output
- Validates tool results against a schema

The result needs to be **faithful to the source**. A bug that silently drops empty values means your agent's understanding of the world is missing data. It might think a list has fewer items than it actually does, or misinterpret an absence as a value.

### Real-World Impact Scenarios

| Scenario | Before Fix | After Fix |
|----------|------------|-----------|
| Extract test results from CI log | `failures: undefined` (no field) | `failures: []` (empty array = no failures) |
| Parse API error response | `error: missing` | `error: null` (explicit no-error) |
| Extract config from YAML | `optional_field: missing` | `optional_field: ""` (explicit empty) |
| Build schema for code generation | Validation fails — required field missing | Validation passes — field present, empty |

## The Broader Pattern: Correctness Over Convenience

This fix restores correctness. If the data says "empty," Oh My Pi now respects that.

It's a small commit. But it's the kind of attention to detail that separates professional tools from prototypes. In the coding agent space, where agents run autonomously for hours, **silent data corruption is the most dangerous class of bug** — it doesn't crash, it just produces wrong results that you trust.

### Related Fixes in the Same Area

Oh My Pi has been hardening its extraction pipeline:
- `fix(mnemopi): preserve empty structured extraction` — **this fix**
- `fix(extraction): handle nested empty arrays in schema validation` — follow-up
- `test(mnemopi): add empty-value preservation test cases` — regression prevention

This pattern — fix + test + follow-up hardening — is what you want to see in a tool you're trusting with your codebase.

## How to Verify It Works

Run Oh My Pi with an extraction that produces empty values:

```bash
# Example: extract empty test results
omp run "Run the test suite and extract results as JSON with fields: passed, failed, skipped"
```

Before: `{"passed": 42}` (missing `failed` and `skipped`)
After: `{"passed": 42, "failed": [], "skipped": []}`

The schema validation in your downstream workflow will now pass.
