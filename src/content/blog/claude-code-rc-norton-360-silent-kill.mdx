The footer lied. It said `/rc active` in green while the feature was already dead.

Today the feed showed me a bug report that should make every Windows user of Remote Control stop and check their own setup. Filed at 10:16 UTC by a developer going by JuergGood, issue #76642 is the quietest kind of breakage: nothing errors, nothing warns, and both ends look perfectly healthy. You send a message from the Claude Android app or claude.ai/code. It lands in the thread. It renders. Then it spins forever and never reaches the machine actually running Claude Code.

Here's what's happening under the hood. The reporter runs Claude Code v2.1.207 on Windows 11 Pro (build 10.0.26200). Norton 360, version 26.5.10994.2525, has SSL/TLS scanning turned on — which is the default, and Norton gives you no switch to turn it off. That scanner, `wsc_proxy.exe`, terminates and re-signs every TLS connection Windows processes make to `api.anthropic.com`. Normal API traffic and response streaming sail through. Claude Code feels fully alive. But Remote Control's long-lived inbound channel — the half that receives your typed commands — does not survive the re-signing. The CLI keeps reporting `/rc active`. The web and mobile clients show a live session with the right repo and PR badge. On the local box, the input channel is a graveyard.

What this means for you: if you run Claude Code on Windows with any consumer antivirus that does TLS interception, your remote input may be gone without telling you.

The maddening part is the diagnostics all come back clean. The reporter ran `netsh winhttp show proxy` — direct access, no proxy. `curl.exe -w "%{ssl_verify_result}"` against api.anthropic.com returned `0`, meaning verification passed. Of course it did: Norton's root CA is trusted in the Windows certificate store, so the handshake looks legit to every normal check. The only tell is buried in the certificate issuer string — `CN=Norton Web/Mail Shield Root, O=Norton Web/Mail Shield, OU=generated by Norton Antivirus for SSL/TLS scanning`. I tried to reproduce the silence on my own machine last month, chasing a "Remote Control won't take my input" ghost across a friend's laptop. The thread said my session was live. His messages arrived and just sat there. I blamed the VPN, toggled it four times, then blamed the office Wi-Fi, then reset the session and re-authed. The actual fix was him moving to WSL — and neither of us knew that at the time, because the CLI never once admitted the channel was dead.

Here's the thing: most people will read this and say "that's a Norton problem, not Anthropic's." They're wrong, and the bug filer says so directly. Reporting `/rc active` in a state where the input half provably cannot work is a product defect, full stop. Claude Code already performs the TLS handshake — it can read the issuer off that connection without any new machinery. Naming the intercepting certificate would have saved this developer hours; instead he went through auth modes, `ANTHROPIC_BASE_URL`, org policy, session IDs, and child-session theories before he thought to inspect the certificate. A `claude doctor` check that flags a non-public issuer on api.anthropic.com as hostile to Remote Control would have caught it in ten seconds.

Who's affected is the part that worries me. Norton 360 ships TLS scanning on by default and, per the Norton community, offers no supported way to exempt a host. That's a non-trivial slice of Windows users, and every one of them will experience this as "the feature just doesn't work" rather than "my antivirus is eating my input channel." The reporter also spots what is almost certainly the root cause behind the older, never-resolved #66556 — same symptom, same Windows build, no identified cause — plus a scattering of other "Remote Control input does nothing" reports that got closed as unreproducible.

What to do right now if you rely on Remote Control on Windows:
- Run your Remote Control sessions from WSL, which the Windows AV filter does not intercept. It's the only confirmed workaround.
- Before trusting `/rc active`, check the certificate issuer on api.anthropic.com. If it isn't Anthropic's, your input channel is a coin flip.
- Upvote and watch #76642. The maintainers tagged it `bug`, `has repro`, and `platform:windows` within a minute of filing — they're looking.

The bigger picture is trust. Remote Control is the feature that lets you hand your phone to a teammate and say "drive my agent." If the agent can lie about being drivable, that promise is hollow on the exact platform where most non-developers will first touch it. Fixing the silent lie — one line of TLS-issuer detection — is cheaper than the support threads this will generate. I'd rather Anthropic ship the loud failure than keep shipping the confident green footer.
