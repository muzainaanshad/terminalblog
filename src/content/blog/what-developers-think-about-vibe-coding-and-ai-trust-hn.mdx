Two Hacker News threads this week captured something the press releases miss: **how developers actually feel about AI coding agents** when the marketing noise stops.

One thread on "vibe coding" drew 11 comments debating whether the term is a useful descriptor or an insult. Another on "when can we trust AI in coding" pulled 7 comments from engineers who've tried to make AI handle full development cycles — and hit walls.

Neither thread is about a product launch. Both are about the gap between what AI coding *promises* and what it *delivers* in daily work.

---

## What Happened: The Term That Divided HN

Andrej Karpathy coined "vibe coding" in early 2025: "forget that the code even exists and fully give in to the vibes." He meant it as a description of a new workflow — letting the model drive while you steer.

HN didn't take it that way.

**The criticism:** "It's hopelessly vague and useless," wrote the original poster (Rabbit504030201). "What does it mean? 'Forget that the code even exists AND fully give in to the vibes'? What vibes? How are vibes defined? Are one supposed to dance freestyle on a flat plain?"

**The defense:** "It accurately describes how most people use AI for code generation," countered krapp. "For every person doing careful, meticulous testing and only using AI to incrementally generate code they personally understand... there are ten thousand 'lol model go brrr' coders who don't care, and don't want to care."

**The middle ground:** spacedcowboy argued the real description is "thinking things into existence" — the human provides vision and yes/no decisions, the LLM handles implementation. "Vibe coding" and "AI slop" are terms "employed by the threatened and the scared."

**The personal take:** danstefancu said they "hate the term 'vibe' anyway. Only appropriate for epilepsy-filled, crowded electronic music dance parties. Using it anything else gives me regurgitation tingling."

---

## Developer Reactions: It's Not About the Term — It's About Trust

The "vibe coding" debate is really a proxy for a deeper question: **how much of the development process can you actually hand off?**

The parallel thread — "Ask HN: When can we trust AI in coding, and avoid the happy path issue?" — lays this bare.

The OP (abalgir) described a setup where Claude Code writes code and Codex tests it, with Codex mandated to refute Claude's results. "Even with such a strict environment, I am ending up with problems... when asking Claude, the answer is 'This is on me; I did not do X and Y'; when I ask it whether Codex checked it, 'Codex checked all but not this...'"

Seven comments followed. The consensus: **AI judgment is still an illusion.**

proc0: "Sometimes it makes good decisions, sometimes not, and that is a huge problem that keeps it from being good agentic systems. They still need the harness and all this other traditional code around it to get it to work."

benatespina: "The art of building software is about slicing the problem into the smallest chunks; the AI has been designed to answer the questions. The new models each time are better at solving hard problems that are related to the essential complexity, but they are not aware of the accidental complexity."

codingdave offered the pragmatic view: "Testing has always been a game of figuring out how much is enough to produce a stable product, without burning massive amounts of engineering time with testing. LLMs have not changed that. They will never be perfect, and that is OK."

## The Real Insight: Harness Engineering > Model Chasing

While HN argues about terminology, a third thread reveals what serious practitioners are actually doing.

pauliusztin reverse-engineered Claude Code, OpenCode, and Pi to understand their "harness" — the scaffolding around the model: prompt management, tool orchestration, context engineering, sandboxing, subagent delegation, benchmarking, replay debugging.

The key finding: **LangChain kept the same model and changed only the harness. Their coding agent went from 53% to 67% on Terminal-Bench — from outside the top 30 to the top 5. Same model. Better harness.**

Ramp (the fintech company) scales operations with a custom harness instead of relying on Claude Code or Codex.

The 8-step harness framework pauliusztin teaches:
1. Design the harness
2. Build the bare-bones agent loop
3. Sandbox it, locally and remotely
4. Apply 4 essential context engineering techniques
5. Add subagents as a context engineering technique
6. Deploy it headless to the cloud: CLI, webhooks, cron
7. Build benchmarks to measure it
8. Replay failed runs to debug agents

This is where the industry is moving: **not better models, but better harnesses around existing models.**

## What It Means for You

### If you're just starting with AI coding
Don't get caught in the "vibe coding" vs. "real engineering" culture war. The term doesn't matter. What matters is:
- **You are the architect.** The model is a very fast, sometimes confused implementer.
- **Never push unreviewed code.** The "lol model go brrr" approach produces exactly what you'd expect.
- **Start with a harness mindset.** Even a simple checklist — "did I read the diff? did tests pass? does this match the spec?" — puts you ahead of most.

### If you're building production systems with AI
The "trust AI" thread is your reality check:
- **AI cannot reliably self-verify.** The Codex-refutes-Claude setup failed because both models drift.
- **You need deterministic guardrails.** Not "another AI watching the AI" — that just adds another failure mode. You need linting, type checking, contract tests, invariant checks that *don't* use LLMs.
- **Invest in harness, not hope.** The teams shipping reliably (Ramp, the harness engineering course builders) treat the model as an unreliable component and build infrastructure around it.

### If you're evaluating coding agents
The Kimi Code thread (waximabbax) tested a $19/month competitor against Claude Code's $20/month:
- Kimi: 1.59M tokens before 5-hour quota hit — **$1.37 of API value**
- Claude Code: ~381M tokens in 4-5 hours on Opus 5.5 xhigh
- **Difference: ~240x more usable capacity per dollar**

Raw model benchmarks don't tell this story. **Quota policies, caching behavior, and harness efficiency determine real-world value.**

## One Concrete Takeaway

If you take one thing from 50+ HN comments this week: **stop evaluating models. Start evaluating harnesses.**

The model is a commodity. The harness — how you manage context, how you sandbox, how you verify, how you replay failures — is where reliability lives. That's what pauliusztin's course teaches. That's what Ramp built. That's what the "trust AI" commenters are discovering the hard way.

The next time someone asks "which coding agent is best?", the honest answer is: **the one with the best harness for your workflow.** And right now, that's something you mostly have to build yourself.
