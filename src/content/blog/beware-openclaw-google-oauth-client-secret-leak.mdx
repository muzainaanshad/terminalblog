## TL;DR

**OpenClaw versions 2026.9.7 through 2026.10.6 (and likely earlier) do not redact Google OAuth client secrets (`GOCSPX-...`) from tool output shown to the AI model.** When an agent reads files like `client_secret.json`, `.env`, or `gcloud` output containing these secrets, they appear in plain text in the model's context window and session transcripts. This affects anyone using Google Cloud, Google APIs, or Google OAuth with OpenClaw.

**Check if you're affected:** Run `grep -r "GOCSPX-" ~/.openclaw/` — if you see results, your secrets may have leaked.

---

## What Happened

OpenClaw (the open-source agent framework behind products like ClawDBot) includes a redaction system designed to prevent secrets from reaching the AI model. It has two code paths:

| Function | Purpose |
|----------|---------|
| `redactModelVisibleToolPayloadText()` | Masks secrets in tool results **shown to the model** |
| `redactSensitiveText()` | Masks secrets in **logs and transcripts** |

The problem: **Google OAuth client secrets use a fixed, recognizable prefix — `GOCSPX-` followed by 28 URL-safe base64 characters — but OpenClaw's redaction patterns don't include this prefix.**

### The Leak in Detail

The reporter tested with dummy secrets across versions 2026.9.7, 2026.9.33, 2026.10.4, 2026.10.5, and 2026.10.6. The results were identical across all versions:

```
redactModelVisibleToolPayloadText  json  LEAK
redactModelVisibleToolPayloadText  bare  LEAK
redactSensitiveText                json  redacted
redactSensitiveText                bare  LEAK
```

**Translation:**
- The **model-visible path** (what the AI actually sees) **always leaks** — both inside JSON blobs like `client_secret.json` and as bare values in command output
- The **log path** only catches the JSON form (via a `client_secret` field-key rule), but **misses bare values**

### Other Google Credentials — Already Protected

For comparison, these Google credential types **are** properly redacted:

| Credential Type | Prefix | Redacted? |
|-----------------|--------|-----------|
| API Keys | `AIza...` | ✅ Yes |
| Access Tokens | `ya29....` | ✅ Yes |
| Refresh Tokens | `1//0...` | ✅ Yes |
| **OAuth Client Secrets** | **`GOCSPX-...`** | **❌ No** |

## Who Is Affected

**You are affected if ALL of these are true:**

1. You use **OpenClaw** (or a derivative like ClawDBot) version 2026.9.7 or later
2. You have **Google OAuth credentials** in your project — typically:
   - `client_secret.json` or `credentials.json` files (downloaded from Google Cloud Console)
   - `.env` files with `GOOGLE_CLIENT_SECRET=GOCSPX-...`
   - Output from `gcloud auth application-default print-access-token` or similar commands
3. Your agent **reads these files** or runs commands that output them (e.g., `cat client_secret.json`, `gcloud config list`, reading `.env`)

**Typical scenarios that trigger the leak:**
- Agent sets up a Google Cloud project and reads the credentials file
- Agent reads `.env` to load environment variables
- Agent runs `gcloud` or `terraform` commands that print credentials
- Any tool output containing a `GOCSPX-...` string

## How to Check If You're Affected

### Quick Check (30 seconds)

Run this in your terminal:

```bash
# Check OpenClaw's local state directory for any leaked secrets
grep -r "GOCSPX-" ~/.openclaw/ 2>/dev/null
```

**If this returns ANY results**, your Google OAuth client secrets have likely been exposed to the model and saved in session transcripts.

### Deeper Check (if you use Git)

```bash
# Check your repo history for accidental commits (run from repo root)
git log --all --full-history --oneline --grep="GOCSPX-" 2>/dev/null
git log --all --full-history -p -- "*.json" "*.env*" 2>/dev/null | grep -i "GOCSPX-" | head -20
```

### Check Your Session Transcripts

If you've been running OpenClaw interactively, your session transcripts may contain the secrets in plain text:

```bash
# Look for GOCSPX in session logs
grep -r "GOCSPX-" ~/.openclaw/logs/ 2>/dev/null | head -10
```

## How to Protect Yourself (Right Now)

### 1. Rotate Any Exposed Secrets Immediately

**This is the most important step.** If the check above found anything, assume the secret is compromised.

```bash
# Go to Google Cloud Console → APIs & Services → Credentials
# Find the OAuth 2.0 Client ID that matches the leaked secret
# Click "Regenerate secret" — this invalidates the old GOCSPX-... value
# Update your local files with the new secret
```

**Do this for every Google OAuth client secret that may have been read by OpenClaw.**

### 2. Stop Storing Secrets in Files Agents Read

Move secrets out of the filesystem where agents operate:

```bash
# Option A: Use a secret manager (recommended)
# - Google Secret Manager
# - AWS Secrets Manager
# - HashiCorp Vault
# - 1Password CLI (op read)

# Option B: Use environment variables injected at runtime
# export GOOGLE_CLIENT_SECRET="GOCSPX-..."  # Only in your shell, not in .env files

# Option C: Use Application Default Credentials (ADC)
# gcloud auth application-default login
# This stores credentials in ~/.config/gcloud/ — outside typical agent workspace
```

### 3. Add a Local Redaction Rule (Temporary Workaround)

If you must keep using OpenClaw with Google OAuth credentials, you can patch the redaction locally:

```bash
# Find your OpenClaw installation
# For npm global install:
OPENCLAW_ROOT=$(npm root -g)/openclaw

# For local install:
# OPENCLAW_ROOT=/path/to/openclaw

# Patch the redaction patterns (backup first!)
cp "$OPENCLAW_ROOT/dist/redact.mjs" "$OPENCLAW_ROOT/dist/redact.mjs.backup"

# Add GOCSPX pattern to the vendor token patterns
# This requires editing the compiled JS — see the fix section below for the exact pattern
```

**Note:** This is a temporary band-aid. The real fix must come from OpenClaw upstream.

### 4. Audit What Else Might Have Leaked

The same redaction gap could affect other vendor prefixes not yet cataloged. Check for:

```bash
# Common secret prefixes that might also be missed
grep -rE "(sk_live_|sk_test_|rk_live_|pk_live_|ghp_|gho_|ghu_|ghs_|ghr_|AIza|ya29\\.)" ~/.openclaw/ 2>/dev/null
```

## Is There a Fix?

### Official Fix Status

**As of October 24, 2026: No official release contains the fix.**

The issue was reported on **October 23, 2026** (OpenClaw issue #181502) with:
- Complete reproduction script
- Root cause analysis
- Suggested fix with exact code changes
- Labels: `security`, `impact:security`, `clawsweeper:source-repro`, `clawsweeper:needs-security-review`, `P2`

The maintainers have been notified. Given the severity (credential leak with high-confidence repro), a patch release is likely imminent.

### The Fix (What Maintainers Need to Do)

The reporter provided the exact fix — add this pattern to two places in the redaction code:

```javascript
// In DEFAULT_REDACT_FIELD_PATTERNS / VENDOR_TOKEN_REDACT_PATTERNS:
String.raw`(GOCSPX-[A-Za-z0-9_-]{20,})`

// Also add to DEFAULT_REDACT_PREFILTER_RE so the fast prefilter doesn't skip it:
/GOCSPX-/
```

And optionally: apply the existing `client_secret` field-key rule to the **model-visible path** too (currently only on the log path).

### When Will a Fixed Version Ship?

Watch these for the fix:
- **GitHub Releases:** https://github.com/openclaw/openclaw/releases
- **Issue #181502:** https://github.com/openclaw/openclaw/issues/181502
- **npm:** `npm view openclaw versions --json` (look for version > 2026.10.6)

**Expected timeline:** Critical security issues in OpenClaw typically get patch releases within 48-72 hours of reporting. Check the issue for updates.

## What This Means for AI Agent Security

This vulnerability illustrates a systemic problem in AI coding agents:

### The Redaction Gap Problem

Agents **routinely read credential files** — it's how they work. They `cat` `client_secret.json`, read `.env`, parse `gcloud` output. The redaction layer is the **only thing** preventing those secrets from reaching:

1. **The model's context window** (where they can be repeated in responses)
2. **Session transcripts** (saved to disk, potentially committed to git)
3. **Log aggregation systems** (if you pipe logs to Datadog, Splunk, etc.)

When redaction misses a prefix, **every agent run that touches that credential type leaks it.**

### Why This Keeps Happening

| Factor | Reality |
|--------|---------|
| **Credential formats proliferate** | Every cloud provider has 5+ secret types with different prefixes |
| **Redaction is pattern-based** | Maintainers must manually add each new prefix |
| **Testing is incomplete** | The OpenClaw repro showed 97/97 boundary-crossing leaks — but only for known patterns |
| **No standardized secret format** | Unlike JWTs or AWS keys, Google OAuth client secrets have no formal spec — just a de facto prefix |

### The Broader Lesson

**Never assume an agent's redaction is complete.** Treat any file an agent reads as potentially visible to:
- The model (and thus any downstream user of that model's output)
- Your local transcript/log files
- Any telemetry the agent sends home

**Defense in depth:**
1. **Don't put secrets in agent-accessible files** (use secret managers)
2. **Rotate secrets regularly** (automate with `gcloud`/`aws`/`az` CLI)
3. **Audit agent transcripts** before sharing or committing
4. **Use read-only filesystem mounts** for agent sandboxes where possible
