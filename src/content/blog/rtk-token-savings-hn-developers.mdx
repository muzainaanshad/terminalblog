A few months ago, a developer asked an AI coding agent to list files in a folder. The agent ran `ls -la` and got back a wall of text: file names, sizes, permissions, owners, dates. All of it landed in the model's "context window" — the memory it uses to reason — and every character of that output costs you money, because AI coding agents are billed per token (roughly every four characters).

RTK, short for Rust Token Killer, is an open-source tool that sits between that agent and your shell. It rewrites command output into a terser form before the model reads it. `ls -la` becomes `644 file 824B` — same file, no owner, no date, far fewer tokens. The pitch is simple and seductive: *cut 90% of the terminal output your agent reads, and your AI coding bill shrinks with it.*

The tool hit 79,000 GitHub stars. A viral X post claimed it could cut Claude Code tokens by up to 60%, racking up 313,000 views. Then the numbers stopped adding up — and a 162-point Hacker News thread with 80 comments turned into one of the most useful debates about AI coding costs this year.

---

## What happened: the benchmark that poked the bubble

The story starts with RTK's own name. "Token killer" implies tokens get killed. But RTK never actually counts the tokens your model is billed for. Its `rtk gain` statistic measures something cruder: the number of bytes of command output removed, divided by four, *pretending* those bytes would have become billing tokens.

Three things happened in September 2026 that put that claim on trial:

1. **JetBrains' SkillsBench evaluation found no savings** from RTK across its test suite.
2. **Quesma, a database observability company, ran its own paid benchmark**: over $1,500 in tokens, 1,740 attempts, two agent setups — Claude Code with Fable 5.0 and OpenCode with DeepSeek V4 Pro — each task run five times with and five times without RTK.
3. The **Hacker News thread** that followed split developers into "it's snake oil" and "show me better data" camps.

Quesma's headline numbers were devastating for the marketing claim. Claude Code's total bill fell about 5% with RTK. DeepSeek's *rose* about 5%. On a per-task average, Claude was 1% *more* expensive and DeepSeek 17% more expensive. Pass rates dipped slightly with RTK in both setups.

And almost all of Claude's savings came from a single task. Remove that one outlier, and RTK's benefit across everything else was under 1%.

The most damning detail was in the `rtk gain` counter itself. At one point, RTK credited itself with 120.5 million "tokens saved" on two calls — 69% of its entire measured savings — for a `head -1` command that would *never* have printed the whole file anyway. One commenter summarized the mechanic in a sentence: an agent runs `rtk some-command-that-prints-100k-tokens | tail -5`, costs a few hundred tokens without RTK, and RTK still reports a 100,000-token victory. The savings it advertises are largely fictional.

## Developer reactions: three camps, one pattern

### Camp 1: "These hacks are snake oil"

The dominant response was blunt. One developer who had evaluated similar tooling called these output-compression tricks snake oil, writing that benchmarks were too expensive to run reliably and everything was "statistical noise" — before promoting his own competing open-source tool in the same comment.

That move did not go unnoticed. The top reply called it out: *why should I trust your benchmarks over theirs when you're peddling the same thing?* The awkward reality is that founders of "vibe-coded token hacks" — RTK, Lumen, Dirac, and a dozen others — mostly benchmark their own tools, and author benchmarks are exactly the ones skeptics have learned not to trust.

One developer described spending *way too long* trying to reproduce another tool's published benchmark results in his own setup, failing, and concluding: "If any person other than the author has time to verify these results, I'd be curious to hear it." Another said he'd tested a similar project and couldn't wring any improvement over plain `rg` (ripgrep). The same verdict kept reappearing: fancy search and compression beat nothing, but plain grep plus a small budget model beat both.

### Camp 2: "RTK actively hurts my agent"

The strongest comments weren't about dishonesty — they were about *confusion*. LLMs are trained on the normal output of bash tools. Feed them an unusual compressed format and they assume something is broken: the file must be missing, the flags must be wrong, the tool must be a different version. So they re-run the command, bypassing RTK, requesting more context, burning *more* tokens than they saved.

> "I kept seeing the model get confused in the reasoning text and retry a command bypassing rtk. I didn't even need a benchmark to see it was regularly an impediment to the final outcome."

One commenter who builds a coding agent tested output compressors firsthand and called RTK "a net negative in both CPU time and accuracy." Another org did the same evaluation and found RTK worsened task performance across the board. A developer who runs RTK on projects with heavy `gh` and `docker` usage said it genuinely helped there — but admitted it did nothing for `grep` and `git`. Even the counter-examples were narrow: a useful tool for *verbose build commands like cargo or maven*, not a universal money printer.

Then there were the bugs. A Quesma test run caught RTK repeatedly rewriting a `find` command it didn't support, producing 339 consecutive errors over 12 minutes — and an attempt that cost roughly nine times the same task without RTK. The developer's verdict was harsher than "overhyped": *if my agent runs `ls -la`, do not drop the owner and date — that's an expected part of the output.* Nothing should be predicting which part of the output you want.

### Camp 3: "The real fix is a cheap subagent"

Buried in the thread was the most practical idea. Instead of compressing output before the model reads it, spawn a *separate cheap model* (a small, fast, inexpensive model like Flash-Lite or Haiku) whose only job is to summarize tool output before it enters the main agent's context. Several developers independently reported this as the only approach that actually generalized in their own benchmarks: the expensive model reads summaries, and the cheap model pays the summarization cost.

A related angle: the entire "hype" industry exists because nobody measures anything. "I no longer trust any claims unless they are backed by benchmark results," said a developer who has spent a year working in this space. "It is possible to reduce token usage. It's just much harder than the basic approach."

## The real insight: token math is not cost math

Every side of this thread converged on one uncomfortable truth: **fewer tokens in, fewer tokens out, and cheaper tokens are three different games.**

Output tokens you don't generate are savings. Output tokens you replace with *confused retries* are not. Compressing `ls -la` saves input tokens but costs reasoning quality — and one confused extra turn wipes out a thousand compressed lines. The Quesma numbers make the tradeoff visible: RTK compressed massive amounts of output, yet total cost barely moved, because the agent's behavior changed in response.

There's also a "bitter lesson" argument that resonated in the thread: models are getting *better* at anticipating large command output and defensively limiting it themselves — using `head`, `tail`, and `grep` on their own. As models get smarter, the compression layer gets redundant. One developer's entire RTK alternative was a single line in his agent rules: *"Cap large/unknown command output: `COMMAND 2>&1 | head -c 4000`."* Empirically, he found RTK made his agents run longer to finish the same tasks.

And the deepest skepticism extended past RTK to the whole economy of "skills" and magic prompt bundles: if a simple pre-processing step genuinely saved money, why wouldn't the AI labs upstream it themselves? The charitable answer — labs have no incentive to reduce your bill — was met with a sharp counter: leaks suggest the labs already train their models to emit fewer tokens. The uncharitable answer, offered by several commenters, is that most of these tools are "putting a wet phone in rice" — a ritual that feels productive and does nothing.

## What it means for you

**If you use RTK or similar token compressors:** the odds are you are not saving what you think. Measure your actual cost per task with and without it — not the tool's own savings counter, your *bill*. If you see wins, they're most likely concentrated in verbose, noisy commands (build tools, `gh`, `docker`), not everyday `grep` and `git` work. Pay attention to whether the agent starts re-running commands or asking for more context; that's the failure mode that eats your savings.

**If you buy into agent "skills" and "hacks" generally:** treat author benchmarks as marketing until independently reproduced. The thread's one universal recommendation — cheap subagent summarization and plain shell primitives — is free, model-agnostic, and was verified by multiple developers. Prefer boring tools you can reason about.

**If you're new to AI coding agents:** this whole debate is a useful lesson in how the economics actually work. You pay for tokens consumed in *every* step of the loop: reading files, running commands, rethinking, retrying. Tools that promise to shrink one step can quietly inflate the others. The developers who control agent costs aren't the ones with the fanciest plugins — they're the ones who cap output, route summaries through cheap models, and watch the *total* bill, not the savings counter.

One line from the thread captures the mood better than any benchmark: *"You use caveman mode to save tokens — I use it to make the agent shut up."* The cost problem isn't really about tokens at all. It's about trust in what your agent is doing with them.
