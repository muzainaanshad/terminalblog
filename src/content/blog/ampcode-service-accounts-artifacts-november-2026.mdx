## The One-Line Summary

**Artifacts (Nov 2):** Documents that live in the thread -- specs, PRDs, diagrams, runbooks -- co-edited by you, teammates, and the agent. Versioned. Searchable. Persistent.

**Service Accounts (Nov 3):** Threads that belong to the team. No single owner. Survives offboarding. Runs on team credentials. The agent becomes a team member, not a personal tool.

## Artifacts -- The Thread Gets a Memory That Isn't Chat

### What It Is

An **Artifact** is a document attached to a thread. Not a message. Not a file upload. A living document that:

- **The agent writes to** (specs, plans, diagrams, runbooks)
- **You edit** (review, correct, expand)
- **Teammates collaborate on** (real-time, like Google Docs but inside the agent thread)
- **Persists across sessions** (close the thread, reopen tomorrow -- it's there)
- **Versions automatically** (every edit tracked)

### Why It Matters

Before: Agent writes a spec in chat. You scroll up to find it. It's buried. You copy-paste to Notion. Context lost.

After: Agent creates `spec.md` artifact. You open it side-by-side with chat. You edit. Teammate reviews. Agent updates based on feedback. The spec **stays with the thread** -- not in a separate tool.

```markdown
# Example: Agent creates a spec artifact
## Thread: "Refactor auth middleware"

Agent: "I'll create a spec artifact for the refactor plan."
-> Creates `auth-refactor-spec.md` artifact

You: *opens artifact, adds "Must support JWT rotation"*
Teammate: *adds "Rate limiting per tenant"*
Agent: *reads both, updates spec, implements*
```

### What Artifacts Can Be

| Type | Example |
|------|---------|
| **Specs / PRDs** | Feature requirements the agent implements against |
| **Architecture diagrams** | Mermaid/PlantUML the agent draws, you refine |
| **Runbooks** | "How to deploy X" -- agent writes, team maintains |
| **API contracts** | OpenAPI specs co-edited with the agent |
| **Test plans** | Agent generates, QA expands |
| **Post-mortems** | Agent drafts from logs, team finalizes |

### The Workflow Shift

**Old:** Chat -> copy -> paste -> Notion/Confluence -> link in PR -> stale in 2 weeks

**New:** Chat `<->` Artifact (bidirectional, versioned, searchable)

The artifact **is the context**. The agent reads it. You edit it. The next agent session picks it up. No context loss.

## Service Accounts -- The Thread Belongs to the Team

### What It Is

A **Service Account** is a team-owned identity for threads. Instead of `anshad&#64;company.com` owning the thread, `team-amp&#64;company.com` owns it.

- **No personal owner** -- thread survives role changes, vacations, offboarding
- **Team credentials** -- uses shared model subscriptions, API keys, cloud access
- **Audit trail** -- every action attributable to the service account, not a person
- **Permissioned** -- workspace admins control which service accounts exist and who can use them

### Why It Matters

**Scenario:** You build a nightly refactor thread. You go on vacation. Thread stops working because *your* credentials expired.

**With Service Accounts:** Thread runs on `team-amp` credentials. Your vacation changes nothing. The thread is **team infrastructure**, not personal automation.

**Scenario:** Teammate leaves. Their personal threads go dark. Credentials revoked. Automation breaks.

**With Service Accounts:** Threads owned by `team-amp` keep running. Zero disruption.

### The Mental Model Shift

| Personal Thread | Service Account Thread |
|-----------------|------------------------|
| Owned by `you&#64;company.com` | Owned by `team-amp&#64;company.com` |
| Your model subscriptions | Team model subscriptions |
| Your cloud access | Team cloud access (OIDC, IAM roles) |
| Dies when you leave | Survives forever |
| Hard to hand off | Built for handoff |
| "My automation" | "Our infrastructure" |

### How to Set Up

```bash
# Workspace admin creates service account
amp service-account create team-amp \
  --model-subscription team-openai \
  --cloud-provider gcp \
  --oidc-role projects/team-amp/roles/amp-runner

# Team members use it
amp thread create --service-account team-amp "Nightly dependency updates"
amp thread create --service-account team-amp "PR review bot"
amp thread create --service-account team-amp "Incident runbook executor"
```

## Together: Artifacts + Service Accounts = Durable Agent Infrastructure

This is the compound effect:

1. **Service Account** gives the thread **permanent identity and credentials**
2. **Artifacts** give the thread **permanent memory and collaboration surface**
3. **Result:** A thread that runs indefinitely, remembers everything, collaborates with the team, and survives any personnel change

### Real-World Pattern: The "Always-On" Team Agent

```
Service Account: team-amp
  Thread: "dependency-updater" (runs nightly)
    Artifact: "update-policy.md" (team maintains)
    Artifact: "changelog.md" (agent appends)
    Artifact: "breakage-runbook.md" (team + agent co-edit)

  Thread: "pr-review-bot" (triggers on PR)
    Artifact: "review-checklist.md" (team defines)
    Artifact: "style-guide.md" (living doc)
    Artifact: "common-issues.md" (agent learns, team validates)

  Thread: "incident-responder" (manual trigger)
    Artifact: "runbook-template.md" (standardized)
    Artifact: "current-incident.md" (real-time collab)
    Artifact: "postmortem-draft.md" (agent drafts, team finalizes)
```

Each thread is **self-contained infrastructure** with its own memory (artifacts), identity (service account), and collaborative surface.

## Quick Start: Your First Service Account Thread with Artifacts

```bash
# 1. Admin: Create service account (one-time)
amp service-account create team-amp \
  --model-subscription team-claude \
  --cloud-provider aws \
  --oidc-role arn:aws:iam::123456789:role/amp-runner

# 2. Create a team thread
amp thread create --service-account team-amp "Weekly security scan"

# 3. In the thread, create an artifact
# Agent: "I'll create a security-scan-config.md artifact for the scan parameters"
# You: *edit artifact to add "scan S3 buckets"*
# Teammate: *adds "check IAM policies"*

# 4. Schedule it
amp thread schedule "Weekly security scan" --cron "0 2 * * 1"

# 5. It runs Monday 2am on team credentials, using team config, producing team artifacts
```

## What's Still Missing (Honest Assessment)

- **Artifact permissions** -- currently thread-wide; no "view-only" for stakeholders yet
- **Service account quotas** -- no per-service-account usage limits (coming)
- **Artifact export** -- no one-click "publish to Confluence/Notion" (workaround: copy from artifact)
- **Cross-thread artifact linking** -- artifacts live in one thread; no native "reference artifact from thread B in thread A"
