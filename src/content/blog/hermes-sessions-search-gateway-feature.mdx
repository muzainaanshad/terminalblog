Hermes Agent just shipped something that makes you wonder why it wasn't there from day one: `/sessions search <query>`.

A single command that searches the full text of all past sessions — not just titles or metadata, but the actual content of every message, every tool call, every result. Type `/sessions search deploy fix prod` and get every session where you talked about deploying a fix to production.

Before this, finding a past session meant scrolling through lists, guessing dates, or remembering exact filenames. Now it's a single command.

## What It Does

The new gateway endpoint lets you search the full text of all past sessions — not just titles or metadata, but the actual content of every message, every tool call, every result. Type `/sessions search deploy fix prod` and get every session where you talked about deploying a fix to production.

### Search Syntax

```bash
# Basic keyword search
/sessions search "authentication bug"

# Boolean operators
/sessions search "deploy AND (prod OR staging)"
/sessions search "error NOT timeout"
/sessions search "refactor \"user service\""

# Scoped search
/sessions search --since "2026-09-01" "database migration"
/sessions search --tool "git" "merge conflict"
/sessions search --model "gpt-5.6" "reasoning trace"

# Output formats
/sessions search "config" --format json    # for scripting
/sessions search "config" --format markdown # for docs
/sessions search "config" --format summary  # default, human-readable
```

### Result Format

Each result shows: date, session ID, message count, model used, matched snippet with context, and a direct open command.

## Why This Changes Everything

The biggest pain point with persistent AI assistants has always been: "I know we talked about this before, but where?" Hermes's mem0 memory system already surfaced relevant facts across sessions. But `/sessions search` goes deeper — it surfaces the full context, not just the distilled memory.

This bridges the gap between "the agent remembers" and "you can find it."

### Memory vs Search: Complementary, Not Competing

| Aspect | mem0 Memory | /sessions search |
|--------|-------------|------------------|
| **What it stores** | Distilled facts, preferences, patterns | Full conversation raw text |
| **Query type** | Semantic ("how do I deploy?") | Exact/keyword ("exit code 137") |
| **Latency** | ~50ms (vector ANN) | ~200ms (FTS5 + ranking) |
| **Privacy** | Encrypted, user-controlled | Local SQLite, never leaves device |
| **Use case** | "Remind me of our API convention" | "Show me the exact error from Tuesday" |

They work together: mem0 suggests *relevant sessions*, search lets you *open and read them*.

## Tech Stack

The feature was built by the Hermes team. It runs through the gateway layer, meaning it works across any connected provider and any device. The search is **FTS5-backed**, the same engine used by SQLite for full-text search — fast, local, no external dependencies.

### Architecture

```
┌──────────────────────────────────────────────────────────────┐
│                      SESSIONS SEARCH                         │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  /sessions search "query"                                    │
│         │                                                    │
│         ▼                                                    │
│  ┌──────────────────────────────────────────────────────┐   │
│  │              GATEWAY SEARCH HANDLER                  │   │
│  │  • Parses query (boolean, scopes, filters)           │   │
│  │  • Validates session access (user owns session)      │   │
│  │  • Builds FTS5 MATCH query with ranking              │   │
│  └──────────────────────────────────────────────────────┘   │
│         │                                                    │
│         ▼                                                    │
│  ┌──────────────────────────────────────────────────────┐   │
│  │              SQLITE FTS5 VIRTUAL TABLE               │   │
│  │                                                      │   │
│  │  CREATE VIRTUAL TABLE sessions_fts USING fts5(      │   │
│  │    session_id,                                      │   │
│  │    message_role,                                    │   │
│  │    message_content,                                 │   │
│  │    tool_name,                                       │   │
│  │    tool_input,                                      │   │
│  │    tool_output,                                     │   │
│  │    model,                                           │   │
│  │    timestamp,                                       │   │
│  │    tokenize = 'porter unicode61'                    │   │
│  │  );                                                 │   │
│  │                                                      │   │
│  │  • Incremental indexing on session write            │   │
│  │  • ~50MB for 10K sessions (compressed)              │   │
│  │  • No external search service needed                │   │
│  └──────────────────────────────────────────────────────┘   │
│         │                                                    │
│         ▼                                                    │
│  Ranked results → formatted output → terminal               │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### Indexing Pipeline

Every session write triggers incremental indexing:

1. **Session ends** → gateway writes messages to `sessions` table
2. **Background worker** (batched, every 30s) → extracts text from:
   - User/assistant messages
   - Tool calls (name, input, output)
   - System prompts (truncated)
   - Model metadata
3. **FTS5 INSERT** → tokenized with Porter stemming + Unicode61
4. **Deduplication** → content hashes prevent re-indexing on replay

**Index size**: ~5MB per 1,000 sessions (average 400 messages each). A year of daily use ≈ 50MB.

### Ranking Algorithm

FTS5 `bm25()` ranking with custom weights:

```sql
SELECT session_id, 
       snippet(sessions_fts, 2, '<mark>', '</mark>', '...', 32) AS snippet,
       bm25(sessions_fts, 10.0, 5.0, 1.0, 1.0, 1.0, 1.0, 0.5) AS rank
FROM sessions_fts
WHERE sessions_fts MATCH ?
ORDER BY rank ASC
LIMIT 20;
```

Weights: message_content (10.0) > tool_output (5.0) > tool_input (1.0) > tool_name (1.0) > message_role (1.0) > model (1.0) > timestamp (0.5).

This prioritizes *what was said* over *who said it* or *which model*.

## Privacy Model: Local-First, Zero Telemetry

This is not a cloud feature. The search index lives in your local SQLite database (`~/.hermes/sessions.db`). Nothing leaves your machine.

- **No external API calls** — FTS5 runs in-process
- **No telemetry** — queries not logged, not sent
- **Encrypted at rest** — database encrypted with user-derived key (same as credential vault)
- **User-controlled retention** — `/sessions prune --older-than 90d` deletes sessions + index entries
- **Portable** — copy `sessions.db` to new machine, search works immediately

### What Gets Indexed (and What Doesn't)

| Indexed | Not Indexed |
|---------|-------------|
| All user/assistant message text | Image/video binary data |
| Tool names, inputs, outputs | Credential values (redacted at write) |
| Model names, token counts | Vector embeddings (mem0 separate) |
| Timestamps, session metadata | Deleted session content (purged on prune) |

**Secrets redaction**: Before any text hits FTS5, the same credential guard that protects API keys scrubs:
- `sk-...`, `ghp_...`, `xoxb-...`, `Bearer ...`
- `.env` values, SSH keys, database URLs
- Anything matching `SECRET_PATTERNS` config

## Practical Use Cases

### 1. Debugging — Search Error Messages Across All Sessions

```bash
# That weird TypeScript error from last month?
/sessions search "TS2322" --format summary

# All sessions with "segmentation fault"
/sessions search "segfault OR \"segmentation fault\""

# Find every time you debugged a specific service
/sessions search "payment-service" --since "2026-08-01"
```

### 2. Knowledge Retrieval — Find That Config Snippet

```bash
# Nginx config you perfected three weeks ago
/sessions search "nginx.conf" --tool "write" --format json

# Kubernetes deployment yaml pattern
/sessions search "deployment.yaml" --model "gpt-5.6"
```

### 3. Project Handoff — Search Decisions Made in Past Discussions

```bash
# Why did we choose Redis over Valkey?
/sessions search "redis OR valkey" --since "2026-07-01" --format markdown

# Architectural decisions recorded in sessions
/sessions search "ADR OR \"architecture decision\""
```

### 4. Learning — See How You Solved Similar Problems

```bash
# All your React hydration fixes
/sessions search "hydration" --tool "shell" --format summary

# Database optimization patterns you've used
/sessions search "EXPLAIN ANALYZE OR \"query plan\""
```

### 5. Team Collaboration (Future: Shared Sessions)

```bash
# When shared sessions land (v0.22 roadmap):
/sessions search --user "@teammate" "deployment checklist"
/sessions search --shared "incident response"
```

## Integration With Gateway Commands

`/sessions search` composes with other gateway commands:

```bash
# Search → open → continue
/sessions search "oauth callback bug"
# → shows session_7f8a2
/sessions open session_7f8a2
# → restores full context, you continue where you left off

# Search → export → share
/sessions search "api design review" --format markdown > api-review.md
# → markdown file with full conversation, ready for Notion/GitHub

# Search → stats
/sessions search "refactor" --stats
# Sessions: 12 | Messages: 340 | Tokens: 180K | Models: gpt-5.6, claude-5
# Avg session length: 28 messages | Date range: 2026-03-12 → 2026-09-28
```

## Performance

| Corpus Size | Query Latency (p50) | Index Size | Build Time (incremental) |
|-------------|---------------------|------------|--------------------------|
| 100 sessions | 15ms | 0.5MB | <1s |
| 1,000 sessions | 45ms | 5MB | ~3s |
| 10,000 sessions | 180ms | 50MB | ~15s |
| 50,000 sessions | 420ms | 250MB | ~60s |

**Optimization**: Queries with `--since` or `--tool` filters use SQLite indexes on `timestamp` / `tool_name` columns *before* FTS5, cutting scanned rows 10-100x.

## Configuration

```yaml
# ~/.hermes/sessions-search.yaml
sessionsSearch:
  enabled: true
  indexOnWrite: true           # index immediately vs batched
  batchInterval: "30s"         # background indexer interval
  maxResults: 20               # default limit
  snippetLength: 32            # chars around match
  ranking:
    messageContent: 10.0
    toolOutput: 5.0
    toolInput: 1.0
    toolName: 1.0
    messageRole: 1.0
    model: 1.0
    timestamp: 0.5
  retention:
    autoPrune: false           # require explicit /sessions prune
    maxAge: "365d"             # suggestion only
  privacy:
    redactSecrets: true        # uses same patterns as credential guard
    encryptIndex: true         # inherits DB encryption
```

## Limitations & Roadmap

**Current limitations:**
- Single-user only (no shared/team search yet)
- No semantic/vector search (mem0 covers this)
- No regex support (FTS5 limitation — use boolean syntax)
- Max 10K results per query (hard limit for UI responsiveness)

**v0.21+ roadmap:**
- **Semantic hybrid search** — combine FTS5 + mem0 vectors for "find sessions about X" + "find sessions similar to this one"
- **Shared session search** — team workspaces with ACLs
- **Search analytics** — "what topics dominate my last 30 days?"
- **Export bundles** — `/sessions export --search "project-x" --format bundle` → portable .hermes-session file
- **Voice search** — `/sessions search --voice` (uses Hermes TTS pipeline)
