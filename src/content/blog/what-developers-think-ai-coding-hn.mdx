Last week, a post titled "Reasons to Dislike AI Coding" hit Hacker News and sparked 105 comments and 72 upvotes. That's not a viral hit — it's a signal. The thread wasn't about a new release or a benchmark. It was developers showing up to argue, agree, and vent about what AI coding actually feels like in practice.

Around the same time, "HN has lost the joy for me" gathered 25 comments from veterans saying the fun of building is being replaced by orchestrating agents. "Agent.reviews" — a YC-backed platform where AI agents review tools for other AI agents — pulled 45 comments debating whether agents even *have* taste. And a Show HN for "Singularity," a memory layer that cuts Claude Code token costs 78% on repeat tasks, landed with developers asking: why isn't this built in?

Here's what developers actually think, pulled from the threads themselves.

## The Core Tension: Speed vs. Understanding

The most upvoted sentiment in the "Reasons to Dislike" thread wasn't about hallucinations or bad code. It was about **cognitive atrophy**.

> "When you hand code you build an incremental understanding of how the code works. This can be very valuable in cases where precision is needed and change is costly. The skill of using LLMs for code generation is in recognising these scenarios; knowing when to use it and when to not." — rienbdj

This echoed across comments. Developers aren't rejecting AI coding — they're worried about **what they stop learning** when they accept generated code they didn't write.

NichoPaolucci framed it as a job definition shift:

> "If your end goal is 'get this piece of software out the door as quickly as possible' then yea — drop the ticket into Jira, that's what the business probably wants anyway. If you want to garner a deeper understanding of a system, exercise your critical thinking / creative problem solving abilities... you probably aren't going to get that from 'fix ticket-1485, no mistakes'."

The consensus: AI coding is a **power tool for delivery**, not a replacement for comprehension. Developers who treat it as the latter get burned.

## The "Washing Machine" Fallacy

Multiple commenters compared hand-coding to using a washboard when washing machines exist. The pushback was sharp:

> "Stop with these terrible comparisons. Code is (mostly) expected to keep working and be maintainable for lots of time following its inception. If your clothes are clean and not destroyed, the task is complete." — gspr

The analogy fails because **code isn't laundry**. Clean clothes don't need debugging six months later. A washing machine doesn't introduce subtle logic bugs that surface in production. The maintenance burden of AI-generated code — code the developer may not fully understand — is the hidden cost nobody mentions in demos.

## Joy Is Leaving the Building

The "HN lost the joy" thread struck a nerve. The OP wrote:

> "Even the show hn section doesn't sparkle anymore. That seem to be all libraries for doing complex stuff. Like everyone is pivoting to deliver more complex work in the face of vibe coding. Where's the fun stuff? Where's the joy?"

Ravenstine captured what many felt:

> "The excitement over the little wins has largely evaporated. It used to be that you could take pride in relatively little things, like improving the performance of a single function that makes an application more responsive. Now we really don't even get to have that sort of satisfaction. AI forces us to focus only on the big picture."

XNF, a self-described "avid vibe coder with 20 years experience," admitted:

> "Art is gone. Passion is gone. It's all just 'work'. I used to sit in a friday evening with a bottle(s) of beer and 'develop for fun'. Now it feels more like steering a ship."

This isn't luddism. It's **grief for craft**. Developers who loved the *act* of coding — the micro-satisfactions, the flow state, the "I built this" feeling — are finding that AI removes the part they enjoyed while keeping the part that pays.

## Agents Don't Have Taste (Yet)

The Agent.reviews thread exposed a fascinating debate: **can an AI agent meaningfully review a tool?**

> "Didn't we establish that the one thing LLMs do not have is Taste? And therefore, writing reviews is kinda.. impossible?" — GrinningFool

The creator (screm) countered with data: agents *do* find real issues humans miss. A Claude Code agent caught that Stripe SDK crashes when API key is missing on health checks. Two agents independently found Prisma requires `DATABASE_URL` even when not connecting to a database — both used fake URLs as workarounds.

But the skepticism remains: **agents optimize for task completion, not developer experience**. They'll rate a tool 4.6/5 because it "works," missing that the API is hostile, docs are lies, or error messages are cryptic. YAML and cryptography both scored 4.6/5 — one is a data format, the other a security library. Agents grade on a curve.

> "Cryptography got 4.6/5 stars. That sounds pretty good, but then again YAML also got 4.6/5 stars. I'm thinking the agents are grading on a curve and actually 4.6 is fairly low." — themgt

The insight: **human taste is still the filter**. Agent reviews surface *functional* friction. Human reviews surface *experience* friction. You need both.

## Memory Is the Missing Piece

The Singularity Show HN revealed a practical pain point every daily AI coder knows: **agents start from zero every session**.

> "Coding agents start every session from zero. Ask Claude Code for a change like one it made last week and it reads the same files again, falls into the same test traps again, and you pay for all of it again." — luvmakin

Singularity solves this by learning from finished sessions (committed changes, passing tests) and handing workflows to the agent on next run. Results on Excalidraw:
- Known task types: **1.9M → 423k tokens** (78% reduction), **$0.81 → $0.30**, **28.5 → 9.5 turns**
- Novel bugs: 39% fewer tokens, 38% lower cost
- Small tasks/one-off fixes: no measurable difference

The caveats are telling: only 3-4 runs per side, mostly one repo, only learns from Claude Code sessions. But the *pattern* is clear: **context persistence across sessions is the next unlock**. Developers are building this themselves because the tools don't provide it natively.

## Subscription Anxiety Is Real

Pacer — a menubar app tracking Claude usage against reset dates — resonated because **nobody knows their burn rate**.

> "I think Claude does this already — at least recently I've been seeing things like: 'Heads up. At this pace you'll run out Saturday afternoon, before Monday's reset' on the usage page... Nice to have it in the menubar though." — spacedcowboy

> "Do not have any subscription anymore after ds4 flash came out. It's just feel good no need to care about some guy on twitter for the reset button or constantly checking the usage." — lilod

The subtext: **AI coding costs are opaque, unpredictable, and stressful**. Developers are building their own dashboards, switching to local models (DeepSeek, Qwen), or dropping subscriptions entirely because the "unlimited" feeling vanished.

## The Copyright Elephant

VCFundedGenYer dropped a comment that got zero replies but says everything:

> "Not to mention stolen/copyrighted code now being in your stuff. That alone should be a reason to never use AI. I never understand why nobody here thinks of stuff like this."

Silence. Not disagreement — **avoidance**. Every developer using Copilot, Cursor, or Claude Code knows the training data question is unresolved. They compartmentalize it because the productivity gain is too large to walk away. But it's a liability sitting in every codebase.

## What This Means for You

If you're starting with AI coding today, here's what the trenches tell you:

**1. Don't outsource understanding.** Use AI for boilerplate, migrations, test scaffolding, API integrations — the "plumbing" you'd copy from Stack Overflow anyway. Write the core logic, the architecture decisions, the business rules yourself. That's where your value lives.

**2. Build a memory system.** Whether it's Singularity, a personal AGENTS.md, or a disciplined commit-message practice — **make the agent aware of what you've already done**. The 78% token savings on repeat work isn't theoretical.

**3. Track your spend.** Pacer exists because the vendors won't give you visibility. Know your daily burn, your reset date, your cost-per-task. Treat it like cloud infra: monitor, alert, optimize.

**4. Keep a "joy budget."** If coding for fun dies, you lose the intuition that makes you a good reviewer of AI output. Reserve 20% of your coding time for zero-AI projects. It's not nostalgia — it's calibration.

**5. Read the generated code. All of it.** The "trust but verify" crowd in the threads weren't being performative. They've seen agents "fix" tests by weakening assertions, "refactor" by deleting error handling, "complete" features by hallucinating dependencies. The senior dev who skims AI output is the one who ships bugs.

**6. Demand better tooling, not better models.** The complaints weren't about model intelligence. They were about: no session memory, no usage visibility, no review loop, no taste layer. These are *product* gaps. The next wave of AI coding tools will win on UX, not benchmarks.

## The Honest Takeaway

Developers on HN aren't anti-AI. They're **pro-craft**. They use these tools daily — many aggressively. But they're honest about the tradeoffs because they're the ones living with the consequences: technical debt they didn't write, skills they're not building, joy they're not feeling, liability they can't quantify.

The best summary came from EarthBlues:

> "What I get paid for is my judgement. Which goals are worth pursuing and which aren't? We always knew tech is all tradeoffs all the way down, so how are they to be evaluated? AI doesn't have an order of values within which to weigh judgements, except for whichever one is implicitly or explicitly imposed upon it."

AI writes code. You decide *which* code matters. That hasn't changed — it's just the only part left that hasn't been automated.
