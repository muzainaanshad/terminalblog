Two threads exploded on Hacker News this week about AI coding agents. One asked a simple question: "Is anybody producing good code with coding agents?" The other laid out "The Four Horsemen of Agentic Coding" — four fundamental problems that emerge when teams adopt these tools at scale.

Together they pulled over 200 comments from senior engineers, team leads, and solo builders. The consensus isn't what the press releases say.

## What happened

On October 2nd, a senior engineer posted an Ask HN that cut through the hype. They described spending entire workdays reviewing AI-generated pull requests — "convoluted code riddled with footguns" — taking 5x longer to review than human-written code. The kicker: they barely understood what they were approving. Each day they drifted further from understanding their own codebase.

That post hit 28 points and 40 comments.

The same day, a Substack article titled "The Four Horsemen of Agentic Coding" hit 111 points and 89 comments. It named four specific failure modes: slop (low-quality code that technically works), alienation (engineers losing connection to their craft), deskilling (atrophy of hard-won expertise), and accountability vacuum (nobody owns the output).

A third thread — Anthropic's own guide to "Getting the most out of Opus 5.5" — drew 152 comments, many from developers sharing what actually works versus what the docs claim.

## Developer reactions: the good, the bad, and the "it depends"

### "The code works but I have no idea how"

This was the most common sentiment. Multiple commenters described the same pattern: AI produces functionally correct code that passes tests, but the implementation choices are opaque. One engineer put it bluntly: "I often discover that they didn't do what I really wanted — sometimes Claude made it faster by incurring expensive costs, or doing a migration that would be risky in prod, or making a tradeoff that's not worth it."

Another described the review burden: "It takes 5x longer to review Claude merge requests and I barely understand what I approve."

### The "vibe coding" trap

Several developers admitted they'd fallen into what one called "vibe coding" — prompting the agent with high-level goals and letting it run. The results were predictable. As one commenter noted: "Specs that gets systematically ignored way too often." Another: "Poorly specified long running tasks is a recipe for 'rollback all those changes...'"

The engineers who reported success shared a specific workflow: write detailed specs in Markdown first, iterate on the spec with the agent, *then* have it implement. One described their process: "Write good specs into files, usually Markdown. Go through the spec files with the agents, have it point out holes and problems, and then update the specs. Go through a few iterations of this and then start your agents on development. Garbage in, garbage out."

### The "two modes" compromise

A surprising number of senior engineers have settled on a hybrid approach. One commenter with 152 upvotes on their approach: "For AI-maintained code (like a GUI to visualize performance data), IDGAF what the code looks like. I just let claude or codex go nuts and 100% vibe code. For code I care about, I audit every single hunk as it's produced. For mission critical code, I write the code myself and have an agent review it."

This "tiered trust" model appeared repeatedly: throwaway code gets full autonomy; core business logic gets human review; critical infrastructure gets human authorship with AI assistance.

### The social fabric is tearing

Perhaps the most striking thread wasn't about code quality at all. It was about team dynamics.

"My work Slack channels are ghost-towns," wrote one engineer. "People are logged in, but they're never saying anything. PRs have their names on them, even the review comments are posted from their accounts, but it is obvious that Claude wrote everything."

Another: "The team thing is killing us right now. Everyone is just kind of silo'd with their agents and they present these entire complex units of work with no input from the rest of the team, and by then it's too late to fix."

A third described the "meat proxy" phenomenon — colleagues pasting raw LLM output into chat instead of answering questions themselves. "Asking a question in search of shared understanding only to be passed the modern equivalent of a LMGTFY link hurts in a very particular way."

### The Opus 5.5 reality check

Anthropic's own thread revealed practical truths the marketing doesn't cover. Developers reported burning $500 in token costs on single sessions. One noted: "Cache reads are priced at 5% of inputs, instead of 10% for previous models" — a meaningful cost optimization but still expensive at scale.

Multiple commenters confirmed the "wall-clock time" problem: Opus 5.5 runs tasks in the background with suppressed output, sometimes waiting 30+ minutes for a timeout when something breaks silently. "It likes to run things in the background with suppressed output, waiting for it to exit before it takes action," one wrote. "Today alone I've had to break in two or three times when something obviously broke and it was sitting for over 10 min."

The cybersecurity refusals were another surprise. Several developers reported sessions being poisoned by the classifier: "Eventually every single response was terminated by the classifier before it even began, with the reason being a placeholder string like `<thinking quote>` or similar."

## The real insight: it's a harness problem, not a model problem

Reading through 200+ comments, a pattern emerges. The developers producing good code aren't using better models — they're using better *harnesses*.

What separates the "it works great" crowd from the "it's slop" crowd:

**1. They treat the agent like a junior engineer, not a magic box.** They write specs, do design reviews, break work into small reviewable chunks, and iterate. "I have it do small chunks I can quickly review, give it feedback, iterate, etc until I like the output, then I move on to the next step."

**2. They invest in tooling around the model.** Custom harnesses with skill selectors, local model routing for cheap tasks, graph-based codebase understanding, automated PR review pipelines with multiple models arguing over changes. One team built a "Minority Report style review skill" with a separate judge model orchestrating code quality, security, and performance reviews.

**3. They accept the cost structure.** The $20/month plan users hit limits fast. The $100/month users burn through $500 sessions. Teams doing this seriously budget for it like cloud compute — because that's what it is.

**4. They don't pretend the code reviews itself.** The "AI reviews AI" approach failed for multiple commenters. Human review remains essential, but it shifts earlier — to the design and spec phase, not the code phase.

## What it means for you

If you're just starting with coding agents, the HN consensus gives you a map:

**Don't start with autonomy.** Start with a spec file. Write what "done" looks like in enough detail that a human junior engineer could execute it. Then hand it to the agent.

**Budget for review time, not generation time.** The 5x review multiplier is real. Plan for it. If you can't review the output, don't generate it.

**Pick your battles.** Not all code deserves the same scrutiny. Internal tooling, prototypes, and one-off scripts are fine for vibe coding. Your authentication system, payment processing, and data migrations are not.

**Build the harness before you scale.** The teams succeeding at scale didn't buy a tool — they built one. Custom agents, local model routing, spec-driven workflows, multi-model review pipelines. If you're rolling this out to a team, allocate engineering time for the harness, not just the subscription.

**Watch the social signals.** If your team Slack goes quiet and PRs become rubber-stamp exercises, you have a process problem, not a tool problem. Schedule human design reviews. Require human-authored architecture decisions. Keep engineers talking to each other.

**The "level 4 autonomy" promise is a trap.** Multiple commenters noted the seductive idea: "reach level 4 autonomy and don't read or write code anymore." The engineers who've gone furthest down this path warn it's a mirage. You either understand your codebase or you don't. When (not if) the agent produces something subtly wrong in a way tests don't catch, you need to understand it well enough to fix it.
