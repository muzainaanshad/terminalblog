## TL;DR

**Hermes Agent 0.22.x had a credential leak in its terminal snapshot pipeline.** When a routed worker (a profile that isn't your default) started a terminal, its login-shell bootstrap sourced your `~/.zshrc` — which many users configure to `export GITHUB_TOKEN=$(grep ... ~/.hermes/.env)` for MCP servers. The `export -p` dump at the end of that bootstrap captured those re-exports into the snapshot file, and **every subsequent `execute()` command in that terminal inherited those credentials**, even though they were never bound to the worker's scope.

**Fixed in PR #142656** (merged to main, will ship in 0.22.3+). The fix adds a snapshot-time exclusion set: any launch-profile `.env` key that isn't explicitly bound to the active profile's scope gets `unset` in the snapshot. Your `~/.zshrc` keeps working for interactive shells; the leak is closed in the agent's snapshot.

Run `hermes --version` after updating. If you're on 0.22.3 or later, you're patched.

## What Happened

### The Architecture

Hermes Agent supports **multi-profile isolation**: each profile gets its own `HERMES_HOME` with its own `.env` (the "launch vault"), its own bound scope (which credentials it's allowed to see), and its own terminal sessions. When you run a **routed worker** — a profile that isn't the launch profile — the gateway spawns a terminal on your behalf with a **scoped credential environment**: only the keys declared in that profile's `credentials.bind` are injected.

The terminal snapshot mechanism (`tools/environments/local.py`) builds a reproducible environment for every `execute()` call:

1. Start a login shell (`bash -l` or `zsh -l`)
2. Source files listed in `terminal.shell_init_files` (typically `~/.zshrc`, `~/.bashrc`)
3. Run `export -p` → write the result to a snapshot file
4. Every later `execute()` sources that snapshot

This gives you a stable environment with your PATH, nvm, asdf, aliases — without re-running the full login shell every command.

### The Leak

Your `~/.zshrc` (or `~/.bashrc`) is **your file**, not Hermes's. Many operators put things like:

```bash
# In ~/.zshrc — convenient for interactive shells
export GITHUB_TOKEN=$(grep '^GITHUB_TOKEN=' "$HOME/.hermes/.env" | cut -d= -f2-)
export FIGMA_API_KEY=$(grep '^FIGMA_API_KEY=' "$HOME/.hermes/.env" | cut -d= -f2-)
export API_KEY_21ST=$(grep '^API_KEY_21ST=' "$HOME/.hermes/.env" | cut -d= -f2-)
```

When a **routed worker** builds its snapshot:

1. The launch profile's `.env` (at `~/.hermes/.env`) is on disk with **all** root-vault keys
2. The login shell sources `~/.zshrc`
3. Your `grep` commands read the launch `.env` and `export` those keys into the shell
4. `export -p` dumps **everything** — including `GITHUB_TOKEN`, `FIGMA_API_KEY`, `API_KEY_21ST` — into the snapshot
5. The Python-side `build_subprocess_env` scope scrub runs **after** the snapshot is created — it never sees these re-exports because they happened inside the bootstrap subprocess
6. **Every subsequent `execute()` in that terminal sources the snapshot and gets those credentials**

The credentials were visible to:
- Every command the agent ran in that terminal
- Any child processes spawned by those commands
- Anything inheriting that environment

### Who Was Affected

**You were affected if ALL of these were true:**

- You run Hermes Agent with **multiple profiles** (routed workers)
- Your `terminal.shell_init_files` includes `~/.zshrc` or `~/.bashrc` (default: yes)
- Your shell rc file **reads `~/.hermes/.env` and exports keys** (common for MCP server auth)
- You ran agents in routed profiles that executed terminal commands

**You were NOT affected if:**
- You only use the default profile (the launch profile) — the fix explicitly skips exclusion for the launch profile
- Your shell init files don't read `~/.hermes/.env`
- You don't use routed workers / multi-profile setups

## How to Check If You Were Exposed

### 1. Check Your Version

```bash
hermes --version
# If < 0.22.3, you have the leak
```

### 2. Check Your Shell Init Files

```bash
grep -n '\.hermes/\.env' ~/.zshrc ~/.bashrc 2>/dev/null
# If this returns matches that export keys, your rc file was the leak source
```

### 3. Check Your Profile Config

```bash
hermes config get terminal.shell_init_files
# Default includes ~/.zshrc, ~/.bashrc
```

### 4. Inspect a Snapshot (Advanced)

If you have an active routed-worker terminal, you can see what the snapshot captured:

```bash
# Find the snapshot file (path varies by profile)
# Look for lines like: export GITHUB_TOKEN=ghp_xxxxxxxxxxxx
# Those should NOT appear in a routed worker's snapshot
cat ~/.hermes/profiles/<profile-name>/.terminal_snapshot_*
```

## The Fix

### What Changed

**File: `hermes_cli/tools/environments/base.py`**

A new module-level helper computes the exclusion set:

```python
def _compute_launch_vault_exclusions_for_snapshot(launch_env_keys: set[str], scope_keys: set[str]) -> tuple[str, ...]:
    """Return launch-vault keys NOT bound to the active scope, upper-cased, sorted."""
    launch_uc = {k.upper() for k in launch_env_keys}
    scope_uc = {k.upper() for k in scope_keys}
    return tuple(sorted(launch_uc - scope_uc))
```

The `LocalEnvironment` class gains:

```python
def _snapshot_excluded_launch_vault_names(self) -> tuple[str, ...]:
    if not self._is_routed_home():
        return ()  # Launch profile: no exclusion, preserve existing semantics
    launch_keys = self._load_launch_profile_env_keys()  # Reads ~/.hermes/.env
    scope_keys = self._get_bound_scope_keys()           # From profile's credentials.bind
    return _compute_launch_vault_exclusions_for_snapshot(launch_keys, scope_keys)
```

The snapshot's `unset` hook (already existing for session vars) is extended to also `unset` these excluded names. The exclusion set is **monotonic** — once a name is excluded, it's never re-introduced in that session.

**File: `hermes_cli/tools/environments/local.py`**

The snapshot bootstrap now calls the exclusion method and passes the names to the `unset` hook.

### Why Not Just "Drop ~/.zshrc"?

The leak source is **your** `~/.zshrc` — which you wrote for good reasons:
- Interactive shells need those exports for MCP servers to work
- Dropping `~/.zshrc` would break your normal terminal workflow
- PATH, nvm, asdf, aliases from `~/.zshrc` are valuable in agent terminals too

The fix **preserves the rc file's contributions** (PATH, nvm, etc.) while **surgically removing** only the launch-vault keys that aren't in the active scope. This is the correct architectural boundary: the snapshot pipeline enforces scope semantics; your shell config stays yours.

## How to Verify You're Patched

### 1. Update Hermes

```bash
# If installed via pip/pipx
pipx upgrade hermes-agent
# or
pip install --upgrade hermes-agent

# If installed via npm
npm update -g @nousresearch/hermes-agent

# Verify
hermes --version
# Should be 0.22.3 or later
```

### 2. Run the Test Suite (If Building from Source)

```bash
cd hermes-agent
python -m pytest tests/tools/test_local_shell_init.py::TestSnapshotExcludesLaunchVaultNamesNotInScope -v
# All 4 tests should pass:
# - test_helper_returns_only_residue_minus_scope
# - test_helper_is_case_insensitive
# - test_launch_profile_target_returns_empty_exclusion
# - test_routed_worker_zshrc_export_excluded_from_snapshot
```

### 3. Manual Verification (Routed Worker)

1. Create a test routed profile with a minimal scope (bind only `TEST_KEY`)
2. Put `GITHUB_TOKEN=ghp_fake` in `~/.hermes/.env`
3. Add `export GITHUB_TOKEN=$(grep ...)` to `~/.zshrc`
4. Start a terminal in the routed profile: `hermes terminal --profile test-routed`
5. Run `execute('env | grep GITHUB_TOKEN')`
6. **Before fix:** `GITHUB_TOKEN=ghp_fake` appears
7. **After fix:** `GITHUB_TOKEN` is absent (unset by snapshot)

## What This Means for Your Workflow

### No Action Required If:
- You're on 0.22.3+ — the fix is automatic
- You only use the default profile — never affected
- You don't put vault reads in your shell rc files — never affected

### Recommended Hygiene (Regardless of Version):

1. **Move MCP credentials out of `~/.zshrc`** — use Hermes's built-in credential binding instead:
   ```yaml
   # In profile config
   credentials:
     bind:
       - GITHUB_TOKEN
       - FIGMA_API_KEY
   ```
   Hermes injects bound keys directly into the subprocess env — no shell rc file needed.

2. **Audit your `~/.hermes/.env`** — rotate any keys that may have been leaked in snapshots before the fix.

3. **Use `hermes secret list`** to see what each profile can actually access.

## Bottom Line

This was a **real credential leak** with a **clean fix**. If you run routed workers and have shell init files that read `~/.hermes/.env`, your agents were seeing more credentials than their scope allowed. Update to 0.22.3+ and the leak is closed — no config changes needed.

The broader lesson: **credential scope enforcement must happen at the snapshot layer**, not just at injection time. Any subsystem that re-materializes environment state (snapshots, caches, checkpoints) is a potential scope boundary violation.
