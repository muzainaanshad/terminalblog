Jonathan Blow — creator of Braid, The Witness, and the Jai programming language — posted a video with a simple question: **if AI solved coding, why is my software still the same?**

The Hacker News thread exploded: 418 comments, 320 points. Developers didn't just watch — they argued, agreed, pushed back, and shared what they're actually experiencing.

This isn't a summary of Blow's video. This is what 400+ developers think when marketing hype meets daily reality.

## What Happened

Blow's core argument: AI writes code faster, but the software we use daily — Outlook, Slack, Jira, your bank's app — hasn't gotten noticeably better. If coding was the bottleneck, removing it should show visible effects. It hasn't.

He suggests the real bottlenecks are elsewhere: understanding what to build, managing complexity, communication, taste. Coding was never the hard part.

HN didn't let that sit. The thread became a referendum on where AI actually helps, where it fails, and whether developers are becoming obsolete or just shifting to different work.

## The Major Camps

### Camp 1: "Coding Was Never the Bottleneck" (Strongest Consensus)

This view dominated. Multiple developers with 20+ years experience echoed Blow:

> "From *The Mythical Man-Month* (1995 ed): 1/3 planning, 1/6 coding, 1/4 component test, 1/4 system test. The separation can be blurred, but it aligned roughly with my experience. Whenever I helped a colleague, coding was not the problem. It was either lack of planning or no test setup. It was never the coding part." — **skydhash**

> "I've been writing code for a long time, and have seen time and again that a lot of problems get solved in code far faster than the organization can absorb the change. This is not universally true, but the number of times I built something in a few days or weeks and waited twice as long for half a dozen handoffs is quite memorable." — **ch4s3**

> "AI practically zeroes out the coding and component test part of the process and massively accelerates the system test. What's left is 'planning' which under a modern iterative model apparently includes deployment/distribution and getting/understanding/incorporating feedback. With a fully optimized process, knowing what to build is nearly the entire problem." — **svachalek**

**The insight:** Organizations spent 20 years optimizing for code velocity. CI/CD, microservices, agile, dev tools — all aimed at shipping code faster. AI just deleted that bottleneck. Now the pain moves to: what do we build? How do we verify it? How does the org absorb it?

### Camp 2: "Software Quality Is Getting Worse, Not Better"

A surprising number of developers argue AI is actively degrading software quality:

> "Now we can make even less functional code much more quickly! All it costs us is some dignity, poor people's electricity rates going up and massive, massive amounts of cash set on fire." — **malfist**

> "Now we have the added benefit of nobody understands it." — **brink**

> "I'm so sick of the whole team not understanding what is going on with Claude written docs and tickets." — **coffeebeqn**

> "Nothing seems functional nowadays. I have a recurring event in Outlook that has a reminder set. If I snooze that reminder, no matter the duration, it will never reappear. This has been a core feature of Outlook for so long that it might as well be considered day-1 functionality. Why it breaks like this in 2026? Who knows..." — **LgWoodenBadger**

The pattern: AI generates code that *works* but isn't *understood*. When something breaks, no one knows why. Technical debt accumulates faster because the human who would have caught it during writing never engaged with the logic.

### Camp 3: "AI Is Incredible — If You Know How to Drive It"

Experienced practitioners push back hard on the pessimism:

> "95% of the time the LLM can turn the requirements into code, faster, cheaper, and with fewer defects on the first attempt, than most humans." — **ch4s3** (in a sub-thread defending AI)

> "I've been doing this with Fable 5.2 as head-orchestrator, Opus sub-orchestrators, and Codex workers. 10+ sub-orchestrators running up to 20 sub-sub workers each. GitHub issues for work tracking + worktrees and PRs to prevent collision. So far it's working very well." — **nickalaso**

> "T3 Code is the best way to interact with AI coding. Works like inbox zero, hiding running threads until Claude needs input or is done. Integration with repo/PR is nice. Ability to have multiple accounts and mix OpenAI/Anthropic/local." — **Vaudtje**

**The divide:** Developers who treat AI as a *tool they direct* report massive gains. Developers who expect AI to *replace their judgment* report frustration. The skill gap is real and widening.

### Camp 4: "The Cost Model Is Broken"

Anthropic's new Claude Code Projects (parallel AI workers) sparked a fierce sub-discussion about token economics:

> "I recently asked Claude what was the best Discord bot library and it spawned 7 sub-agents and ran me completely out of usage in about 10 minutes. I think this won't be particularly helpful until we solve the problem of usage exploding like that." — **bcherny**

> "Its easy to fix. I've run into the same issue on day one... Just tell your claude session to be 'head-orchestrator' and delegate to Sonnet or Opus rather than more Fable agents. The fable-making-fable thing also made my usage evaporate." — **nickalaso**

> "It's a product to burn through tokens at an alarming pace." — **gib444**

The parallel-agent model is powerful but expensive. Developers are building their own orchestration layers (head-orchestrator → cheaper sub-agents → cheapest workers) to stay within budget. The platform defaults are seen as wasteful.

### Camp 5: "Cloud-First Is a Trap"

Multiple developers rejected Anthropic's cloud-first approach for Projects:

> "So this only works in anthropic cloud? I started feeling the push last month with the free cloud-only credits. With Nvidia's GPUs now under control, open weight producing buyers are crippled. Anthropic is turning the screws. The agent must represent the individual, not the organization. What future do you want?" — **throwaway13337**

> "This has a lot of friction. Claude Projects concepts is great... but this being cloud first is confusing to me and may be others as well. It asks too much permissions when working with local projects which become annoying after some time." — **enraged_camel**

> "Projects instead defaults to a less advanced coordinator... then the smarter worker subagents start, but I don't get to talk to them directly unless I hunt them down, and then they fire off threads which I have NO visibility at all into and have no idea what they're doing." — **russellbeattie**

Developers want local-first, controllable orchestration. Cloud defaults feel like lock-in. The "coordinator" abstraction removes visibility that experienced users rely on for debugging runaway agents.

### Camp 6: "I Feel Useless — And That's the Point"

A poignant Ask HN thread from the same week captured the emotional undercurrent:

> "I solo founded a SaaS in 2019... Today most of the code is fixed and AI handles most of what is left, I even wrote the harness for AI to replace me. And I feel more and more useless on my own project. Those are the periods I remember with pleasure. A team was stuck, I came in, and things started to work. At this point, I should've found something else to do, a bigger problem to solve, but I feel kinda stuck." — **hellohiki**

Responses ranged from "find the part AI can't do" to "that feeling is the transition — you're becoming an architect, not a builder." But the anxiety is real: when the craft you built your identity on becomes automated, what's left?

## The Real Insights (What the Thread Actually Reveals)

### 1. The Bottleneck Shift Is Real — And Painful

Organizations spent 20 years optimizing for code velocity. AI just deleted that bottleneck. Now the pain moves to: **what do we build? how do we verify it? how does the org absorb it?**

Companies that don't restructure around the new bottleneck will just generate more code faster — code that sits in PR queues, breaks in production, or solves the wrong problem.

### 2. Understanding > Generation

The developers getting the most value aren't "prompting better." They're building **harnesses**: orchestration layers, evaluation loops, verification gates, context management. They treat AI as a high-variance worker that needs guardrails, not a magic box.

> "A lot of what I do with AI is write *requirements*. Which is horrifying to engineers for some reason." — **bsenftner**

Writing precise requirements — the "what" and "why" — is becoming the high-leverage skill. The "how" is increasingly automated.

### 3. Local-First Tooling Wins for Serious Work

Cloud IDEs and cloud agent orchestration are fine for demos. Production developers want:
- Local execution (no permission prompts for every file write)
- Worktree/parallel session management they control
- Token budget visibility and limits
- Integration with their existing Git/PR workflow

Tools like **T3 Code**, **poundlock-dispatch**, and custom orchestration scripts are filling this gap because the platform offerings don't.

### 4. The "Junior Developer" Model Is Dangerous

Treating AI like a junior dev who needs code review works for small tasks. At scale, it fails because:
- Juniors learn; AI repeats the same mistakes unless the harness catches them
- Juniors ask clarifying questions; AI hallucinates confidently
- Juniors have intuition about system boundaries; AI optimizes locally

The winning pattern: **AI as a specialized worker (code gen, test gen, refactor) + human as architect/verifier + automated evaluation gates.**

### 5. Cost Anxiety Is Changing Behavior

Developers on Pro/Max plans are actively architecting around token limits:
- Head orchestrator (expensive model) → sub-orchestrators (mid-tier) → workers (cheap/fast)
- Explicit token budgets: "use around 300k tokens"
- Offloading to local models (Codex, Antigravity, DeepSeek) via custom MCPs

This is creating a two-tier ecosystem: those who can afford unlimited cloud compute, and those building sophisticated local-first pipelines.

## What It Means for You

### If You're Just Starting with AI Coding

**Don't expect magic.** The "chat with AI, get working app" demos work for greenfield toys. Real codebases need:
1. **Context management** — AGENTS.md, CLAUDE.md, or equivalent so AI understands your conventions
2. **Evaluation harness** — automated tests, linting, type-checking that run on every AI change
3. **Orchestration** — even a simple script that runs AI → checks output → feeds back errors

Start with one tool (Claude Code, Cursor, or Codex). Learn its limits. Build a harness. Then add parallelism.

### If You're Already Using AI Daily

**Audit your harness.** The developers winning are those who:
- Measure "cost to resolution" not "lines of code generated"
- Have automated gates that catch AI errors before human review
- Use cheaper models for 80% of work, expensive models only for architecture/verification
- Keep local control — avoid cloud lock-in that removes visibility

### If You're Leading a Team

**The bottleneck moved.** Your job isn't "ship more features." It's:
- Define what "good" looks like (requirements, acceptance criteria, architecture guardrails)
- Build the evaluation infrastructure so AI output is verified automatically
- Restructure team workflows around *decision-making* not *code production*
- Budget for token costs — they scale non-linearly with parallel agents

### If You're Feeling the "Useless" Anxiety

**You're not becoming obsolete. You're becoming an architect.** The craft shifts from "writing syntax" to "designing systems that verify themselves." The developers who thrive are those who:
- Build tools that make AI reliable (eval harnesses, orchestration, context systems)
- Focus on the 20% of decisions that determine 80% of outcomes (architecture, data models, interfaces)
- Accept that "writing code" is now a commodity skill — "deciding what code should exist" is not

## The Uncomfortable Truth

The HN thread reveals a split that won't close:

**Developers who build harnesses around AI** → 10x output, higher quality, more control.

**Developers who chat with AI and hope for the best** → frustration, technical debt, feeling replaced.

The tooling is converging (Claude Code, Cursor, Codex, GitHub Copilot all adding parallel agents, MCP, local execution). The differentiator is **who builds the guardrails.**

Blow asked why software hasn't improved. The answer in the thread: **because most teams are using AI to write more code faster, not to build better verification loops.** The teams building harnesses *are* shipping better software — you just don't see it because it's internal tools, bespoke automations, and infrastructure that doesn't have a marketing page.

The avalanche hit coding. The avalanche hitting *software engineering* — the discipline of building reliable, maintainable systems — is just starting. The developers who survive it are the ones building the avalanche shelters now.
